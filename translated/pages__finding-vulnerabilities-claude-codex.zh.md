# 使用 Claude Code 与 OpenAI Codex 在现代 Web 应用中发现漏洞

我们对 AI 编程智能体寻找漏洞能力的深入研究表明：存在令人意外的优势、关键的弱点，以及一个严重的「一致性」问题。

Romain Gaucher

Vasilii Ermilov

Clint Gibler

2025 年 9 月 2 日

##### 分享

**TL;DR**：我们评估了 AI 编程智能体在真实代码中寻找漏洞的有效程度。

**方法**：我们让 Anthropic 的 Claude Code（v1.0.32，Sonnet 4）与 OpenAI Codex（v0.2.0，o4-mini）在 11 个流行且大型的开源 Python Web 应用中发现漏洞。二者合计产生了 400 多条安全发现，由我们的安全研究团队逐一评审。

**AI 编程智能体能发现真实漏洞**：Claude Code 发现 46 个漏洞（真阳性率 TPR 为 14%，假阳性率 FPR 为 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。其中约 20 个是高危漏洞。

**AI 能理解上下文，却卡在数据流上**：Claude Code 最擅长发现不安全的直接对象引用（IDOR）缺陷，真阳性率（TPR）为 22%（13 个正确问题/59 条报告），但在跨多个文件与函数执行污点追踪时表现吃力，SQL 注入的 TPR 仅为 5%（2/38），XSS 为 16%（12/74）。OpenAI Codex 几乎报不出正确的 IDOR，TPR 为 0%（0/5），在 SQL 注入上表现极差（0%，0/5），XSS 也是 0%（0/28），但出人意料地报告了比 Claude Code 更多正确的路径穿越问题，TPR 为 47%（8/17）。

**非确定性是真正的难关**：在完全相同的代码库上多次运行完全相同的提示词，往往得到差异极大的结果。在其中一个应用中，三次完全相同的运行分别产生了 3 个、6 个和 11 个不同的发现。

**关键要点**：

- 带有相对简单的安全导向提示词的 AI 编程智能体，已经能在真实应用中发现真实漏洞。
- 但是：取决于漏洞类别，结果可能相当嘈杂（假阳性率高），尤其是在 SQL 注入、XSS 与 SSRF 这类传统注入型漏洞类别上。
- 详细的评估与基准测试是理解某种方法在发现漏洞时有多有效的关键（这一点向来成立，在 LLM 这类非确定性工具上更是如此），也是判断你的改进是否走在正确方向上的依据。

## 引言

在 Semgrep，我们与应用程序安全（AppSec）朝夕相处。长期以来，我们一直在产品中把 AI 投入生产（Assistant 背后的技术、用于测试我们 AI 工作流的 promptfoo、用安全研究员分诊来评估自动分诊的表现），持续研究传统确定性分析与现代 AI 上下文能力的最佳组合，而不是追逐潮流。

这项研究是那一持续使命的一部分。我们正开启一次深入而公开的探索，以回答一个人人关心的问题：LLM 在源代码中寻找漏洞到底有多有效？

## 关于基于 AI 的漏洞狩猎的开放研究问题

为了引导我们的调查，我们把「LLM 擅长找缺陷吗？」这个宽泛的问题拆解成更具体、可度量的子问题。

- 基于 LLM 的漏洞发现的假阳性率与假阴性率是多少？它会因编程语言、框架、代码库规模或漏洞类别而变化吗？它对代码的写法有多敏感？
- 造成假阳性与假阴性的常见原因是什么？
- 分析有多确定性？每次都能得到相同结果吗？

具体到注入类漏洞，我们想知道：

- LLM 在追踪用户输入从源（source，例如用户提供的值）到汇（sink，例如消费原始 SQL 查询的方法）之间的流动上有多有效？
- 它能跨函数与文件追踪数据吗？
- 它能对净化函数（sanitization function）与其他安全控制进行推理吗？
- 它能对来自第三方开源依赖的函数进行推理吗？

## 常见 SAST 基准测试的问题：缺乏真实感

在深入我们的发现之前，先谈谈我们如何衡量 AI 的表现。当前许多研究/论断所依赖的基准测试，虽然有其价值，却没有完全体现真实世界代码的复杂性。

**带已知漏洞的应用**：这些基准测试只使用带已知漏洞的开源应用；多亏 Kinnaird McQuade，其中许多可以在 vulnerable-apps 中找到。如果你读过这个博客，可能会认出其中一些名字，如 WebGoat、JuiceShop、OWASP Benchmark 等。但它们存在一个问题：当前的 LLM 很可能已摄入过这些仓库的代码，以及互联网上大量公开的漏洞分析文章，从而拥有先验知识并扭曲结果。这些代码往往并不真实，充斥着大量注释、标注和变量名，暗示甚至直接说明漏洞在代码中的位置或如何利用。有时，工具的输出结果甚至被提交进了仓库。来自 javaspringvulny 的 SearchService.java

来自 juiceshop，挑战名称本身就是文件名的一部分……

**XBOW** 为自动化渗透测试工具提供了基准测试，但并不适用于静态分析：这些代码往往过于人为造作、过于简化，无法代表真实应用。ZeroPath 在对其做净化处理方面做得很好，但只有一小部分被净化。此外，这些测试用例都是微型应用，专为模拟某个特定攻击场景而设计。若只看 Python 基准测试，XBOW 有 45 个；45 个不同的微型应用，平均不到 98 行代码、3 个 Python 文件。这太小了，无法体现跨整个代码库或多个函数进行搜索与推理的复杂性。

**CVE 记忆偏差**：由于 LLM 是在互联网海量公开数据上训练的，其中包括发现并修复过 CVE 的那些代码库，这就造成了根本性的数据污染问题。AI 可能并不是通过新颖的分析发现了漏洞，而只是识别出它在训练中记住的模式。

近来，学术界设计了诸如 CyberGym、Eyeballvul 或 SecVulEval 之类的基准测试。它们有很大进步，更贴近真实案例，但缺乏对现代 Web 应用的关注，或者把漏洞与更大的应用上下文割裂开来。

**EyeballVul**：来自 Timothée Chauvin 的一个较新基准测试，它从开源项目中提取经过人工审核的真实漏洞，并以最小可复现测试用例的形式呈现。虽然基于真实代码，但它仍把漏洞与更广泛的应用上下文隔离开来，使搜索问题变得更简单。

**SecVulEval 与 CyberGym**：这些套件旨在评估 C 或 C++ 中的漏洞。虽说在各自领域内很有价值，但它们聚焦于 C 和 C++，意味着这些数据并不适用于主导现代云原生开发的 Python/JavaScript 及其他以 Web 为中心的语言。

尽管这些方法各自都有用、有时也该使用，但它们未必反映现代软件开发的实际。真实世界的应用不是干净、孤立的函数，而是依赖、框架与业务逻辑构成的复杂网。

我们的方法不同。我们测试了 11 个大型、基于 Python、持续维护的开源项目，它们使用常见的 Web 框架（Django、Flask、FastAPI）编写。我们的方法与前述方法互补，并且我们认为它的独特之处在于：a) 力求代表真实世界中 AI 驱动的漏洞发现（而非小型、孤立的合成样例）；b) 不受模型训练数据污染；c) 代表了大多数开发者和公司实际在构建的应用类型——使用现代语言与框架的 Web 应用。

### 我们的发现

Claude Code 与 Codex 今天都很有用：它们能发现真实的安全漏洞，但非常嘈杂。整体噪声仍然很高，不过它们在这些流行的开源 Python Web 应用中确实找到了真实的安全漏洞。总体而言，Claude Code 发现了 46 个漏洞（TPR 14%，FPR 86%），Codex 报告了 21 个漏洞（TPR 18%，FPR 82%）。

**许多 IDOR 缺陷起初看起来是对的，Claude Code 还给出了可信的修复建议**：LLM 不仅能发现这些缺陷，还能提出可信的修复方案，例如依据代码中既有模式注入新的权限检查。IDOR 问题可能很难分诊，我们不得不对其中大多数做实测才能确定，这使真阳性率大幅降低。

**Claude Code 作为良好的安全护栏工具？** 许多发现虽然在技术上属于假阳性，但仍然是不错的「护栏」建议，或看起来像。例如，模型常常建议对一个本已安全的 SQL 查询做参数化处理。这虽不算漏洞，却增强了代码。我们仍将其视为假阳性，只是没有其它那些严重。不过这些代码加固建议并不能总是被信任。我们发现若干实例，尤其在客户端 JavaScript 代码中，AI 试图修复它所认为的 DOM 操作问题，但实际上破坏了代码（在我们观察到的案例中是对 HTML 做了双重转义），而那里本来就没有安全问题。

**XSS 与 SQL 注入——难以把各部分拼在一起**：模型难以从服务端框架一路追踪数据到客户端组件（XSS 的常见模式），也难以穿透复杂的应用层次。它常被静态定义的数据搞糊涂，或未能识别服务端的净化处理。

**重复提示词有助于得到更多结果**：LLM 的概率性质意味着，用略微不同的方式问同一个问题可能带来新发现，凸显出分析的不一致性。在同一代码库上多次重复同一提示词，会得到不同的答案，但最终会绕回到同样的发现上。

**OpenAI Codex 有时未能报告有效的 SARIF**。我们预期的 66 份报告中，有 9 份并非有效 SARIF。我们考虑了那些文件里报告的所有发现，但它们不是有效的 SARIF 或 JSON。在我们尝试的所有案例中，Claude Code 都没有这个问题。

## 同样的代码、同样的 AI，每次都是不同的缺陷：AI 编程智能体的非确定性问题

为探索非确定性在实践中如何体现，我们选取其中三个应用，针对同一个安全问题（IDOR）用同一提示词多次运行。一个规律浮现出来：我们每一次运行，AI 的发现都不一样。

在漏洞检测的语境下，这是个大问题。首先，作为安全工程师，我们理想上希望对「代码已针对重要漏洞类别被扫描过」有比「我希望这次模型搜得够彻底」更强的保证。

其次，间歇性地检测出漏洞，会在你的安全工具或漏洞管理系统中造成不一致与噪声。例如，如果你使用 SAST 平台、ASPM，或内部自建的系统，这类系统往往假设此前检测到的漏洞一旦不再出现就意味着已被修复。但在 LLM 驱动的检测中未必如此：单次扫描可能漏掉它，于是后续扫描重新发现同一问题时会被当作「新」发现，产生重复的 JIRA 工单，让开发者沮丧。

以下是我们观察到的一些具体例子：

- **PY-APP-007**：第一次运行中，AI 识别出一个「缺少搜索授权」漏洞，而另外两次运行中都不存在。第二次运行报告了该次特有的问题。第三次运行又发现了它自己独有的一组漏洞。
- **PY-APP-006**：情况类似：第一次运行在用户 API 中发现一个漏洞，而后续运行则聚焦于代码库的不同部分，如事件摘要与笔记模块。
- **PY-APP-002**：这里的变异性或许最为明显。识别出的漏洞数量从第一次运行的 3 个跳到第二次的 6 个，再到 11 个。每次运行呈现的发现都只有部分重叠。

那么，背后的原因是什么？我们认为关键因素是所谓的上下文腐化与压缩（compaction）。当一个 AI 智能体被要求分析整个代码库时，它面对的是海量信息：上下文腐化导致它无法准确从自身上下文中检索。为应对这一点，LLM 会使用某种有损压缩（有时称为 compaction），这意味着函数名、路径等更精细的推理细节可能在摘要过程中丢失。

把它想成试图概述一部长而复杂的小说。你会抓住主要情节点，但必然会漏掉一些细微之处。同样，AI 可能丢掉某个特定的架构模式或细微的数据流，从而在某次运行中漏掉一个漏洞，而在另一次运行中又能抓住。我们在 PY-APP-006 中看到一个清晰的例子：AI 提出的某个修复并不完整，因为它没有复用既有的用户授权基类——那是关键的一块上下文，似乎在那一特定运行中丢失了。

这种非确定性对我们如何推进 AI 原生 SAST 有重大影响。一方面，AI 每次「思考」方式不同，意味着它能探索更广泛的潜在攻击向量，就像一支视角各异的人类渗透测试团队。另一方面，它引入了某种不确定性，可能导致混乱或错误行为。

**覆盖不完整**：单次运行可能给出虚假的安全感，因为它可能漏掉后续运行会抓到的关键漏洞。

**缺乏可重复性**：无法复现结果，使得验证 AI 的发现、以一致且可重复的方式信任其输出变得困难。

**成本与时间上升**：为获得更完整的图景而多次审计，会显著增加所需时间与算力。注意：对传统软件而言，一旦写好，再次运行它基本是「免费」的（不含硬件、电费等成本）。对重度依赖 LLM 的工具则不然——在这个案例中，读入一个代码库并对其推理，每次扫描可能产生数十到数百美元的 Token 成本。今天这些模型的成本可能随时间下降，但更新的模型可能更贵。

## Claude Code 新的 `/security-review` 命令有多有效？

Anthropic 为 Claude Code 发布了一个新命令，名为 `/security-review`。它被设计为在拉取请求（PR）上运行，检查改动的文件并提问以识别具体安全问题。你可以在这里找到该提示词。

当在整个代码库上运行该命令时，我们发现它识别出的安全问题相当有限。很多时候，它找不到我们每次只让 Claude Code 搜索某一类特定安全问题时所得到的问题。

我们在 PY-APP-003、PY-APP-002 与 PY-APP-008 上运行了该命令，三者在整体实验中总共只找到 1 个 XSS，与整体实验的结果差异很大。

## 回答我们的问题

让我们基于所学，重新审视最初的研究问题。

**假阳性/假阴性率是多少？** 对真实世界代码直接使用原始 AI 时，假阳性率非常高：最好的情况是 Codex 的路径穿越 53%，或 Claude Code 的 IDOR 78%；最差的情况是 Claude Code 的 SQL 注入 95%，以及 Codex 的 SQL 注入或 IDOR 100%。不同应用之间的表现也差异巨大：从 PY-APP-002（Claude Code）100%（10/10）的真实 IDOR，到 PY-APP-007 的 0%（0/7）。跨所有应用与所有已报告问题，Claude Code 发现 46 个漏洞（TPR 14%，FPR 86%），Codex 报告 21 个漏洞（TPR 18%，FPR 82%）。由于我们使用的是真实应用，本实验中无法准确度量假阴性。我们将在后续博客文章中介绍度量假阴性率的技术！

**它为什么失败？** 我们观察到的主要弱点是缺乏对代码执行在注入类问题上的深层语义理解。模型难以处理过程间的污点流与隐式流——这正是传统 SAST 引擎通常擅长的领域。其中一些局限也来自上下文压缩与上下文腐化。我们会继续更细致地探究这些局限，并探索缓解它们的方案。

**脚手架与智能体工作流有多重要？** 它们不只是重要，而是正变得不可或缺。AI 在安全评审中的未来不是一个单一、庞大的模型，而是一个由 AI 智能体（在本案例中包括编程智能体）构成的系统，它们能使用工具、对证据做推理，并协作发现和验证漏洞。虽然我们（目前）还没有关于「使用能访问 Claude Code 的智能体」与「更典型的上下文工程（即为推理模型构建提供所有相关代码的脚手架）」之间差异的数据，但我们观察到系统在走完复杂流程、并在汇报安全问题过程中做出有依据决策的能力上存在巨大差异。话虽如此，一个反例是 Sean Heelan 如何通过充分的上下文工程，让推理模型报告出一个漏洞（成功率 8%）。我们强烈建议你读他的博客文章。

**这一切的成本呢？** 遗憾的是，我们未能统一追踪 Claude Code 与 Codex 的成本。Claude Code 的总成本是 114 美元，涵盖所有这些漏洞与所有应用（不含非确定性测试与 `/security-review` 命令的运行）。

## 数据集：未来发布

我们今天不会发布数据集，也不会公布所分析开源应用的名称，因为我们正处于负责任披露过程中，正在联系应用开发者以修复并验证全部安全问题。一旦完成，我们就会放心地发布数据。

## 结论

LLM 不是明天就能取代人类安全工程师的银弹；事实上，它们在端到端发现高危注入类漏洞方面相当弱。然而，它们是一个极其强大的工具。我们的研究表明，通过理解它们的优势（上下文推理）与弱点（代码的深层语义），并借助先进的静态分析引擎围绕它们构建精密的智能体系统，我们可以创造出远胜以往任何工具的新一代安全工具。

## 要点回顾

- 用 Claude Code 与 OpenAI Codex 对 11 个真实 Web 应用（约 7k 文件、超过 800kLOC）做自动化漏洞挖掘，共报出 445 项发现。
- 现有 SAST 基准存在系统性偏差：XBOW 的 45 个 Python 用例规模过小（均不足 98 行、最多 3 个文件），CVE 类数据集带有记忆偏差，EyeballVul 缺少应用上下文，SecVulEval 与 CyberGym 偏向 C/C++。
- 实测效果有限：Claude Code 报出 46 个漏洞（真阳性率 14%、假阳性率 86%），Codex 报出 21 个（真阳性率 18%、假阳性率 82%）。
- 结果具有非确定性：同一目标在不同轮次会得到不同结论，受上下文腐化与上下文压缩、覆盖不全等因素影响。
- 可复现性差、成本随代码规模上升，是这类方案落地的主要障碍。
- IDOR 类漏洞的修复建议质量较高、较为可信。
- 误报并非全无价值，可作为护栏（guardrails）加以利用。
- 结论：智能体审计目前更适合与人工审查互补，需要可复现的基准与人工复核作为前提。
