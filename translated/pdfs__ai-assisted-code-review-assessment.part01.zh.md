摘要

现代代码评审（modern code review）是一种流程：代码作者提交的增量代码贡献，在被提交到版本控制系统之前，由一个或多个同伴进行评审。现代代码评审的一个重要环节，是核实代码贡献是否符合最佳实践（best practices）。其中一些最佳实践可以自动核实，但另一些的核实通常留给人评审者。本文报告了 AutoCommenter 的开发、部署与评估——这是一个由大语言模型（large language model, LLM）驱动的系统，能够自动学习并强制执行编码最佳实践。我们为四种编程语言（C++、Java、Python 和 Go）实现了 AutoCommenter，并在一个大型工业环境中评估了其性能与采纳情况。我们的评估表明，一个用于学习与执行编码最佳实践的端到端系统是可行的，并且对开发者工作流有积极影响。此外，本文还报告了将此类系统部署给数以万计开发者所面临的挑战，以及由此得到的经验教训。

1 引言

现代代码评审 [21, 23]（相较于整体式代码评审 [8]）多年来在开源与工业环境中自然发展起来。一套共同的同伴评审标准已经形成 [5, 20, 21]，其中包括编码最佳实践。许多公司、项目乃至编程语言都以“风格指南”（style guide）[1–4] 的形式对其做出正式定义，这些指南通常涵盖以下方面：
• 格式：行长限制、空白与缩进的使用、圆括号与方括号的位置等；
• 命名：大小写、简洁性、描述性等；
• 文档：文件级、函数级及其他注释的预期位置与内容；
• 语言特性：在（代码）不同语境下对特定语言特性的使用；
• 代码惯用法：使用代码惯用法以提升代码清晰度、模块化与可维护性。

开发者普遍报告对现代代码评审流程有较高的满意度 [23, 28]。其主要好处之一，是为那些不熟悉代码库、特定语言特性或常见代码惯用法的代码作者提供学习体验。在评审过程中，一位专家开发者会向代码作者传授最佳实践知识，同时评审（并了解）代码贡献及其影响。

linters [15] 等静态分析工具可以自动核实代码是否符合某些最佳实践（例如格式规则），有些工具甚至能自动修复违规。然而，细微的准则或带例外情况的准则很难被完整地自动核实（例如命名约定，以及遗留代码中合理的偏离），而有些准则根本无法用精确规则来刻画（例如代码注释的清晰度与具体性），只能依靠人的判断与开发者集体知识。因此，通常期望由人评审者检查代码变更是否存在最佳实践违规。

代码评审流程最大的成本是所需的时间，尤其是专家开发者的时间。即使已有大量自动化，并且流程已尽可能轻量，一名开发者仍可能每天轻易投入数小时于此 [23]。机器学习的最新进展，尤其是大语言模型（LLM）的能力，表明 LLM 适合用于代码评审自动化（例如 [11, 16, 17, 24–26]）。然而，围绕大规模部署端到端系统所面临的软件工程挑战仍未得到探索。同样，对此类系统在整体有效性与用户接受度方面的外部评估也尚付阙如。

本文研究是否可能部分自动化代码评审流程，特别是最佳实践违规的检测，从而为代码作者提供及时反馈，并让评审者能专注于整体功能。具体来说，本文报告我们在 Google 这一工业环境中开发、部署和评估 AutoCommenter——一个自动化代码评审助手——的经验，如今它每天被数以万计的开发者使用。

综上，本文的贡献是：
• 一个基于 LLM 的代码评审助手系统的通用架构（第 3 节）。
• 对工具校准及其部署给数以万计开发者的描述（第 4 节）。
• 对系统的评估（第 5 节）。
• 经验教训的总结与讨论（第 6 节）。

2 背景

AutoCommenter 是在 Google 的大型工业环境中开发的。Google 的现代代码评审实践与其他工业及开源项目类似 [23]。

2.1 代码评审流程

Google 的代码评审流程成熟、基于变更（change）且有工具辅助。Ivanković 等人 [12] 和 Petrović 等人 [18] 提供了该流程的详细总结。对代码库的每一次变更都必须由至少一名其他开发者评审。每天，数以万计的代码库变更经历评审流程，数以万计的开发者以代码作者和评审者的身份参与该流程。

作者与评审者通过代码评审系统交换评论，评审则在受变更影响的文件快照之间推进。每条评审者评论都附在特定文件快照中特定的行与列范围上。为解决一条评论，作者通常会在其本地副本中修改文件，并导出新的快照以进行下一轮代码评审。当作者与所有评审者都满意、且没有任何自动化分析阻止合并时，代码即被合并进代码库。

代码评审流程中最昂贵的部分，是代码作者与评审者“护送”（shepherding）一次变更所花费的时间（从最初编码，到处理评审者评论、确保所有自动化分析通过，直到最终将变更合并进代码库）。尽管该流程已通过自动化系统在评审前分析代码而得到优化（尤其是无需人工干预的自动代码格式化），代码评审每年仍耗费数千开发者的工作量。因此，即便是个位数的百分比节省，也能转化为显著的业务影响。

2.2 最佳实践

最佳实践（best practice）是指被公认为更优的某种特定编程语言用法，而一份最佳实践文档描述它应当如何应用以及带来哪些好处。最佳实践 URL 指代一份最佳实践文档或其特定小节，而最佳实践违规（best practice violation）指代不遵守某项最佳实践、但可以被修改以遵守它的特定代码片段。若从上下文来看足够清楚，我们使用术语 URL 和 violation 分别指代最佳实践 URL 和最佳实践违规。

Google 的中心代码仓库包含多种语言的代码，其中 C++、Java、Python 和 Go 每一种都超过 1 亿行 [19]。有 15 种不同语言拥有对所有开发者都易于获取的正式风格指南。其中许多语言还有额外的语言入门材料、核心库文档，以及技巧周报式通讯。虽然这些材料不像风格指南那样被严格强制执行，但它们在代码评审中被频繁引用。有些语言的此类文档多达数百页。代码作者与评审者都被期望核实代码遵循所有最佳实践。

一种名为“可读性”（readability）的正式机制在十多年前引入，用于确保最佳实践得到一致遵循。某一语言中专职的风格专家被称为“可读性导师”（readability mentor），他们引导经验不足的开发者逐步精通该语言 [23]。可读性导师通常用几句话概括一条最佳实践，并在评论末尾附上一个 URL 供变更作者参考。图 1 展示了一条由可读性导师发布的评论示例。

可读性流程存在一些缺点。对作者而言，它因额外的评审轮次而延长了开发时间。对可读性导师而言，它可能变成一项单调且耗时的工作。它要求掌握数百条不断演进的最佳实践，包括识别并废弃过时规则，并在代码评审系统里（附上相关链接）记录它们。此外，它还要求持续跟踪，有时要经过多轮迭代，确保所有违规都得到纠正。

3 方法

针对第 2.1 节与第 2.2 节所述挑战，我们开发了 AutoCommenter，一个能自动检测最佳实践违规的代码分析工具。它旨在为代码作者提供及时反馈，减少人工最佳实践评审的需求，从而让评审者能专注于代码功能。

3.1 模型与任务定义

自动化最佳实践分析需要一个能够表示源代码、定位违规位置并识别所违反最佳实践的模型。我们以基于 T5、使用 T5X [22] 的传统 Transformer 方法，瞄准一种文本到文本（text-to-text）的转换。最佳实践分析是多任务大序列模型中的一项任务。除了 T5 的标准预训练任务（span 去噪，即预测被掩码的 token）之外，用于训练该模型的其他任务还包括代码评审评论解决、下一次编辑预测、变量重命名，以及构建错误修复 [9]。训练语料由超过 30 亿个样本组成，其中最佳实践分析数据集贡献了约 80 万个样本。模型使用此类模型典型的交叉熵损失进行训练，并针对最大化序列准确率（sequence accuracy）指标进行了调优，即为每个样本预测出精确的目标文本。

对于最佳实践分析，模型的输入是一个任务提示（prompt）和源代码，目标是源代码中的一个位置以及一条最佳实践违规的 URL。任务提示被格式化为一条固定文本的代码注释，使用该编程语言恰当的注释风格。它以自然语言描述任务，并置于源代码之前；源代码是某个文件的直接文本表示。若输入超出模型上下文窗口，则会被截断。位置是源代码中的字节偏移量，URL 则指向被违反的最佳实践。一种领域特定语言定义目标格式，其中一种特殊情况是“空”目标，即不存在任何违规。除目标外，模型还输出一个介于 0 到 1 之间的置信度分数。

考虑以下 Go 语言的输入/目标示例。

输入
```go
// [*] Task: Check language best practices.
// Package addition provides Add
package addition
// Return a sum
func Add(value1, value2 int) int {
    return value1 + value2
}
```
目标
```
INSERT 153 COMMENT https://go.dev/doc/comment#func
```

输入的第一行是固定文本的任务提示；其余部分是源代码。目标给出了位置（字节偏移量 153 对应 `Add` 函数的起始处）和一个 go.dev URL，指向 Go 语言风格指南中该函数注释所违反的确切部分（此例中是注释应以函数名开头的常见做法）。请注意，根据源代码中违规数量的不同，目标可能包含零个、一个或多个（拼接起来的）位置-URL 对。

3.2 模型训练

图 2 展示了模型训练流水线的架构，它由三部分组成。我们将数据集创建拆分为两步（预处理与整编），因为第一步要对大得多的数据量进行操作，因而代价高得多。预处理步骤的输出与模型的输入/目标表示无关。这种分离通过支持对样本表示和其他样本级调整进行快速迭代，提升了特性交付速度（feature velocity）。预处理步骤使用容错调度系统，并周期性地提取相关代码评论，以确保新数据随时可用。

3.2.1 大规模预处理。训练样本由真实代码评审数据创建，但并非所有代码评论都适合用于模型训练。因此，预处理步骤会识别相关代码评论（relevant code comment）——即含有指向最佳实践文档的 URL 的人工撰写评论。对每条评论，预处理步骤随后收集对应的源代码与相关元数据，包括该评论在源代码中的位置及其创建时间。该步骤的输出是一组相关代码评论，每条都带有为模型训练整编样本所需的全部数据。

3.2.2 数据集整编。数据集整编是单个按需执行的加工步骤，以 Beam¹ 流水线实现。它依据第 3.1 节所述的输入/目标格式，将每条相关代码评论转换为标准的 TensorFlowExample 数据结构。

3.2.3 训练与微调。整编后的样本直接用于模型训练与评估。我们在一个 TPU 集群上使用 T5X 框架 [22]，每 1000 步保存一次模型检查点，并使用 Tensorboard 监控训练。

3.3 模型选择

在历史数据上进行的两次内在评估（intrinsic evaluation），为我们选择模型检查点、置信度阈值和解码策略提供依据。第一，在验证集与测试集上的评估，给出基于单文件（per-file）的精确率与召回率估计。第二，在完整历史代码评审上的评估，给出每次代码评审评论总数的估计，表明开发者会多么频繁地与 AutoCommenter 交互。

3.3.1 在验证集与测试集上的评估。我们对数据集进行时间切分，以确保模型没有在验证集与测试集中代码评论的未来代码评审快照上训练过。在我们的数据集中，85% 的文件恰好有一条相关代码评论，11% 有两条，4% 有三条或更多。若预测的代码位置与 URL 与期望值匹配（不考虑顺序），我们便认为该预测是正确的。

回忆一下，模型会为每个预测给出一个置信度分数，这引入另一个参数：若某预测的置信度分数低于某个阈值 t，则可将其抑制。我们将 Precision_t 定义为置信度分数大于 t 的正确预测数，除以置信度分数大于 t 的全部预测数；类似地定义 Recall_t。这些定义让我们能够估计，作为 t 的函数，会有多少（不）正确的结果展示给用户。Precision_t 与 Recall_t 在训练期间被用于比较模型检查点。

虽然这一评估避免了数据泄漏，并让我们能自动评估模型性能，但它有一个局限：虽然可以合理假设给定代码评审快照的人工评论是正确的，但它们并非穷尽的。换言之，给定代码评审快照中的代码可能依据多项最佳实践都有改进空间，但人评审者并未对所有这些都发布评论（附带 URL）。这可能有几种原因：
• 缺少引用：评审者可能评论了某个问题，但没有把 URL 作为引用包含进去。
• 选择性评论：评审者可能只就某个问题评论一次，期望作者在整体上应用修复。
• 专长或关注点不同：评审者可能并不熟悉所有最佳实践，或只是在某次代码评审的语境下选择不评论某问题（例如只关注已改动的代码）。

虽然我们数据集中大多数文件只有一条相关评论，但基于人工检查“不正确”预测的轶事证据表明，由于上述原因，通常可能存在多条最佳实践评论。鉴于我们的真值（ground-truth）数据并不完整，我们的精确率与召回率度量是有噪声的。

¹https://beam.apache.org/

因此，我们采用一种互补的评估，接下来描述，以提升对模型整体性能的信心。

3.3.2 在完整历史代码评审上的评估。为准确估计线上环境中的潜在评论量，我们在使用特定模型检查点与阈值的情况下，在一组历史代码评审上评估 AutoCommenter。预测出的评论不会被追溯性地发布到代码评审系统中，而是记录到数据库中以供分析。这让我们能够估计预期的发布频率——既有单文件粒度，也有单次代码评审粒度。由于开发者是就一整组须经代码评审的代码变更与 AutoCommenter 交互，这一评估是生产部署前的重要一步。作为一个额外好处，这一步还允许针对不同用户群、编程语言等进一步优化并评估发布频率。

3.4 推理基础设施

AutoCommenter 的核心是一个中心化的最佳实践分析服务。该服务接收一个或多个源文件进行分析。对每个文件，它构造模型输入（第 3.1 节），将其编码为标准的 TensorFlow Example 数据结构，并查询模型。模型本身由模型服务提供，该服务使用 TensorFlow 的 Example 数据结构作为领域无关的输入输出格式。最后，最佳实践分析服务执行一系列过滤步骤（第 4 节），抑制低质量预测，并返回剩余预测。

3.5 IDE 与代码评审集成

开发者以两种方式与 AutoCommenter 的分析服务交互——直接通过 IDE 插件，或间接通过代码评审系统。代码评审系统被 Google 所有开发者使用，而 IDE 被几乎所有开发者使用。

AutoCommenter 的评论在 IDE 中作为诊断信息出现，以蓝色波浪下划线标记，横跨相关代码片段。将鼠标悬停于下划线代码上会显示完整评论，其中包含对该最佳实践的简要概括，并含有一个指向相关最佳实践文档的可点击链接。这些内嵌信息消除了开发者在不熟悉最佳实践时于 IDE 与网页浏览器之间来回切换的需要，从而简化了工作流。由于 IDE 中的评论需要实时生成，我们的目标是让评论生成具有亚秒级时延。

在代码评审系统中，AutoCommenter 在每次更新后（即每个新的代码评审快照上）运行，若检测到任何违规便自动发布评论。自动化工具产生的评论在视觉上与人产生的评论相似，但背景颜色不同。

图 3 展示了 AutoCommenter 在代码评审系统中生成并发布的一条示例评论。请注意（右侧的）点赞与点踩按钮，作者与评审者若觉得某条评论特别有用或没用可以点击。另请注意（左侧的）“Please fix”按钮，它对评审者可见。若点击它，就会生成一条新评论，表明该评审者认为这条评论很重要，必须在代码合并进代码库之前处理。这些反馈按钮是代码评审系统的标准功能，出现在自动化工具（例如 [7, 13]）生成的所有评论上，并为工具的用户接受度提供信号。IDE 也提供类似的反馈机制。

要点回顾

• 现代代码评审中，最佳实践的合规性主要依赖人评审者核实；静态分析工具（如 linters）只能覆盖可精确定义的部分。
• AutoCommenter 是一个基于大语言模型（LLM）的系统，为 C++、Java、Python、Go 四种语言自动学习并执行编码最佳实践，已在 Google 大规模部署。
• 任务被建模为文本到文本（text-to-text）转换，基于 T5/T5X：输入为固定文本任务提示加源代码，目标为违规位置（字节偏移量）与最佳实践 URL，并附带 0–1 的置信度分数。
• 训练流水线分三部分：大规模预处理（周期性提取含 URL 的相关代码评论）、数据集整编（按需，Beam 流水线转为 TensorFlow Example）、训练与微调（TPU 集群、T5X、每 1000 步保存检查点）。
• 模型选型依据两类评估：验证/测试数据集上的单文件精确率与召回率，以及完整历史代码评审上的评论量估计。
• 真值数据不穷尽（缺少引用、选择性评论、专长差异）导致精确率/召回率度量有噪声，因而需要互补评估。
• 系统双通道集成：IDE 侧以蓝色波浪下划线呈现、悬停显示并追求亚秒级时延；代码评审系统侧在每个新快照上自动运行，并提供点赞/点踩与“Please fix”反馈按钮。
