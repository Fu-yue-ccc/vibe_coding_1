# 如何高效地进行代码评审：一位 GitHub 资深工程师的理念

GitHub 资深工程师 Sarah Vessels 探讨她的代码评审理念、好的代码评审与坏的代码评审之间的区别、她寻找与评审代码的策略，以及如何从对她自己代码的评审中获得最大收益。

Sarah Vessels · @cheshire137

2024 年 7 月 23 日

| 16 分钟

分享：

作为 GitHub 的一位资深工程师（staff engineer），代码评审是我日常工作中最主要的关注领域之一。在过去八年里，我评审了 7000 多个拉取请求（PR）。为什么这么多？因为代码评审对构建优秀软件至关重要，而多一双眼睛往往能发现你本来会遗漏的问题。

我把代码评审看作我工作中最重要的方面之一。事实上，每当我看到有同事的拉取请求已准备好接受代码评审时，我更愿意放下自己正在处理的分支，转而去评审他们提出的改动。毕竟，他们的拉取请求已经通过了持续集成（CI）的重重考验，也达到了他们自己对于「完成」的判定标准，所以它大概比我自己尚未完成的工作更接近可交付的状态。比起再花上不可预知的更多时间去完成我自己的代码，我更愿意先把他们的代码推过终点线。

我越早给出反馈——「这里可能是 nil，会导致错误」、「这看起来是一个 n+1 查询」、「这个方法能有个方法签名就更好了」——这些反馈就能越快得到处理，缺陷被消灭、功能被发布。

我想分享我进行代码评审的方式，希望我们都能交付更好的代码。

## 什么是代码评审？

严格来说，代码评审——在 GitHub 上通过拉取请求评审来实现——允许协作者对拉取请求中提出的改动发表评论、表明自己对改动的批准，或在拉取请求被合并前要求进一步修改。

我把拉取请求看作一场对话的开端。我把它读作作者在说：「我认为这改进了我们今天的做法。」代码评审是塑造产品实现方式的绝佳机会。作为代码评审者，我的职责是与作者来回讨论，通过提问、质疑假设、以及总体上充当第二双眼睛，来改进他们的代码。

## 打磨你的代码评审流程

### 如何找到待评审的拉取请求

我就住在我的 GitHub 通知收件箱里。它是我在浏览器中固定为标签页的少数几个页面之一，因此随时可用。每当我等待 CI 时、处在任务间隙时、刚开始一天的工作时，或一般有空闲片刻时，我都喜欢查看收件箱。我评审的大多数拉取请求都是在那里找到的。GitHub 的各团队往往会有一个特定的 Slack 频道作为大本营，那是个分享已就绪待评审拉取请求的好地方——这是我发现拉取请求的另一条主要途径。

我还很成功地使用 GitHub 的 Slack 集成，让某个 Slack 频道订阅与我团队相关的新拉取请求。为了筛选哪些拉取请求会出现在 Slack 中，我会使用一个团队专属的标签，然后在 Slack 里用 'subscribe' 命令，形如 ` /github subscribe your/repo pulls +label:"your-team-label" `。

我喜欢用诸如 ` is:open archived:false is:pr org:github -is:draft team-review-requested:github/relevant-codeowner-team ` 这样的查询，来搜索可能待评审的未处理拉取请求。借助这个查询，我能找到 GitHub 组织内处于打开状态、未归档、不是草稿、且已将相关代码属主团队列为被请求评审者的拉取请求。我通常会省略 ` review:required ` 这一搜索限定符，因为即使某位同事已经评审过，我仍有兴趣评审这个拉取请求。毕竟，评审代码不仅帮助作者，也帮助我及时了解影响我所负责代码的变更。

### 用评审者团队来管理通知

你不会希望代码改动去惊动一个庞大的团队，以至于团队里每个人都以为评审这个改动不是自己的责任。这可能导致拉取请求要么无人问津地搁置，要么在还不该合并时就被合并，因为关键的评审者在通知的洪流中错过了它们。这两种情形都会影响产品质量。

我建议，如果可能的话，精简你所加入的代码属主团队的数量，让通知保持在可管理的范围内。这样一来，落到你收件箱里的拉取请求就不再只是噪音，而是你确实觉得应该评审的东西。虽然庞大、包罗万象的代码属主团队作为兜底选项还行，但它们不适合作为自动评审请求的第一道默认选择。要让仓库的 CODEOWNERS 文件保持良好组织，并配套定义清晰的代码边界，以限制通知数量、帮助评审者避免通知疲劳。

限制团队通知的另一种方式，是创建一个第一响应者（first responders）团队，然后用自动化按排班增删团队成员。这样就能让团队专注于他们的日常代码库，而被排班的第一响应者则会收到团队服务区域里拉取请求的通知。例如，使用 PagerDuty API，你可以确定某一天谁是第一响应者。然后你可以使用 Octokit 库来增删团队成员。

### 用自动化在各团队间统一代码评审

仓库级别的配置与自动化，例如使用 CODEOWNERS 文件和分支保护规则，有助于在各团队间强制统一评审流程标准。而其他标准，比如拉取请求中什么值得评论，则必须由我们人类来维护。把你们团队内部代码评审的运作方式记录下来，确保任何提供代码评审或提交拉取请求的人都知道如何让自己的拉取请求得到评审、评审的预期周转时间，以及正在使用哪些自动化来促进评审。

有些团队用项目看板来跟踪有哪些拉取请求进入评审；我见过这种做法对一个管理共享 API 的团队很有效——共享 API 是一个常被团队之外的人修改的领域。其他团队则只依赖 GitHub 通知，我见过这在代码属主划分得很细、且团队纪律严明地一有拉取请求就评审时效果很好。

如果你遵循的是你们团队特有的流程，自动化可以帮助你与团队之外的人沟通预期。例如，如果许多其他团队依赖你们团队的评审，你可以用一个机器人，在任何请求你们团队评审的拉取请求上自动留言，告诉作者他们大约何时能得到你们的回复。

## 什么样的代码评审算好，什么样算坏？

好的代码评审带来清晰性，并推动代码进入比起初更好的状态。

作为评审者，沟通的清晰性是关键。你要让人清楚哪些评论属于个人偏好，哪些是批准与否的阻塞项。给出你所建议做法的示例，可以提升你的代码评审，让你的意思更加明确。如果你能从与拉取请求相同的仓库里给出示例，那就更好了——这会通过鼓励实现方式的一致性，进一步支持你的建议。

相比之下，糟糕的代码评审缺乏清晰性。例如，不给任何评论就一概批准或一概拒绝，会让拉取请求的作者怀疑这次评审是否彻底。哪怕只是用你的批准复述一遍你对拉取请求作者意图的理解，也能暴露你和作者的理解是否一致。

一次没有说清其建议应在何时落地的代码评审，对作者来说也可能是糟糕的体验。指出那些未改动过的既有代码应当重构、或某个额外情况应当处理，这没问题，但重要的是要说明这些是否是批准的前提条件。如果这个拉取请求即使不采纳你的建议也可以落地，一定要讲明。保持一个较小的差异（diff）并把那些改动作为单独的拉取请求分开交付，可能更稳妥。

下面这条代码评审评论展示了具体性，并清楚地传达了所建议的实现方式：

「我看到你的新方法与这个文件中现有的风格一致，接收 [X] 个参数。参数这么多会损害可读性，也意味着这个函数做的事太多。你觉得在后续的拉取请求中重构这个方法以及现有的方法，减少它们接收的参数数量，怎么样？」

这条评论好在哪些方面：

提供了具体的细节。

引用了具体的代码或问题。

提出了问题的解决方案。

引用了证据或给出了解释。

而在光谱的另一端，下面是一些本可以更好的评审评论示例：

「我不喜欢这个。」——评审者不喜欢的是什么？他们心里有没有一个可以明确说出来的替代方案？

可能的改进：

「这一行做的事太多，我们能不能简化它来提升可读性？」

「我认为这会因为 n+1 查询而出现性能问题。」

「我们能不能改用 [首选框架] 的解决方案，而不是自己写一套自定义实现？」

「这样行不通。」——为什么这些改动行不通？

可能的改进：

「这样行不通，因为 [X]，参见这个相关问题：[问题链接]。」

「这个之前在 [拉取请求链接] 里试过，因为 [X] 没成功。」

「如果你在 [X] 上遇到问题，可以改试 [替代方案]。」

「我认为这修复了一个缺陷。」——我喜欢这种点名，但是否有更多上下文，比如问题链接，可以让这一点更清楚？

可能的改进：

「我认为这修复了 [问题链接]。」

「这是在修复 [问题链接] 里的那个缺陷吗？」

「这看起来像我们在 [失败构建的链接] 里遇到的那个缺陷。谢谢修复！」

## 如何给出好的代码评审

### 提问

我把拉取请求的作者看作对其拉取请求所做改动掌握最多上下文的人。我可以基于自己的经历——在 Ruby on Rails 单体应用、TypeScript，或在承担大量流量的数据库中工作的经验——指出我看到的问题，但我信任作者对我所提问题的回答。我把他们对具体细节的理解看得比我的更可靠。

我还很喜欢问涉及代码中所做假设的问题。他们处理的数据是什么形状？是否存在与该形状不匹配的数据？代码能否很好地应对这种数据？代码是否资源密集？性能是否良好？作为评审者，我最喜欢的回应是作者提供一个自动化测试，来验证这些情形下的行为。我第二喜欢的回应是实证数据，比如来自我们数据仓库的查询，或一张显示为什么这些情形不成问题的 Datadog 图表。

作为拉取请求作者，我很感激收到提问。当有人提问时，这为我创造了空间，去解释我为何对自己的改动有信心，并在必要时引用问题、查询或图表。这也让我能把自己的知识与经验分享给他人。作者不仅能看到我的回应，其他评审者以及日后可能追溯某个过往决策上下文的读者也能看到。

### 给出肯定

除了提问之外，对拉取请求中你认同的部分发表评论也是一种好做法。这类评论可以表明你读过并理解了正在被改动的内容，或者表明你验证了代码中的某个假设。举几个例子：

「看起来这与本模块中其他类所用的模式一致。」

「谢谢你为这个加了测试！」

「这比之前可读性高多了。」

以我的经验，收到这类评论本身也让人愉快。收到代码评审有时会让人感到疲惫。当我要应对来自好几方的提问和建议时，收到几条对我无所要求、反而支持和认可我已完成工作的评论，会是一种很好的鼓舞。

### 留意偏见与假设

人们很容易让自己对评审者、或对他们正在改动的代码领域的偏见，影响到自己的评审。你会习惯某个人在某个领域工作、或具有某种资历，于是假定他们知道自己在做什么——但每个人都会犯错。你对他们的改动所投去的目光、你检验他们假设或验证自己假设的提问，可能在上线之前就逮住一个问题。

我非常重视写测试，因为测试能去掉一些偏见。当你写一个测试来检查代码是否正常工作时，你就不必只听作者的一面之词，你只需看测试是否通过——当然，前提是你把测试写对了。😅

我也非常重视让初级开发者在代码评审中向资深开发者提问，即使他们认为自己的问题很傻、或答案显而易见。如果对你来说不明显，这也是合理的。对别人来说同样不会显而易见！把问题提出来，为作者创造空间写下他们的回答，并把这点教育留给后来的人。

### 批准还是不批准

我把自己的评审看作一道可能阻止他人改进我们产品的阻塞关口，所以我凭着良心谨慎地不予批准。我常常会有个人偏好，并建议作者做一些可选的改动，但我不会仅凭这些就不予批准。如果我对某人的拉取请求有建议，但他们的拉取请求按现状不会搞坏生产环境、不会对用户造成负面影响、也不会引起其他问题，我就会带着这些评论给予批准。作者可以选择在合并拉取请求前处理我的反馈，也可以在另一个分支里跟进。

评审代码时，要记住你的建议有多重要。为让你的建议得到处理而推迟发布，值得吗？让作者经历「看到你的反馈、做出建议的改动、等 CI、再次评审、部署、最后合并」这一整套循环，值得吗？如果某个建议不做也不会让谁的日子更难过，那就让作者自行决定是否改、以及何时改这个建议的改动。

「请求修改（Request changes）」选项会阻止拉取请求被合并，直到评审者回来批准它。我很少使用它，因为它通常显得过于强硬。我信任我的团队知道何时该批准一个拉取请求，所以同事的批准可以代替我自己的批准。同样，我信任拉取请求作者会尊重并考虑我的反馈，而不是仅仅因为别人批准了、我没批准就盲目合并。大概只有在我认为存在紧迫的安全问题、并且担心他们在合并前看不到我的顾虑时，我才会选择「请求修改」选项。

## 如何从代码评审中获得最大收益

### 评审你自己的代码

GitHub 高级软件工程师 Paul Smith 教会我在请别人评审之前先评审自己的拉取请求，我也建议你这么做。先过一遍，在那些不明显、或如果你在别人拉取请求里看到就会发问的改动上留下行内评论。自我评审还能帮助判断一个拉取请求是否太大、是否拆分成多个会更好。

特别推荐：如果你在意让自己的拉取请求保持小巧，可以利用 lerebear/sizeup-action，自动给拉取请求打上标签，标示其复杂度与规模。

### 欢迎合并后的评审

如果我碰巧在有人来得及评审之前就合并了一个拉取请求，我仍然欢迎他们的评审。如果我的拉取请求弄坏了什么东西、或带来了意料之外的后果，在拉取请求上就此留下评论，就留下了那条面包屑线索，帮助日后的读者查明发生了什么！

如果我收到对一个已合并拉取请求的评审，我会像它在落地之前那样处理这些反馈。也许是留一条评论解释我的视角，也许是再开几个拉取请求来迭代我最初交付的代码。也许是新开一些议题来记录还有哪些工作要做。

### 使用草稿拉取请求

当你创建一个新的拉取请求时，可以选择把它设为草稿。我大量依赖草稿阶段来表明我是否想要评审。例如，如果某个必需的 CI 构建失败了，或我还没做完，我就会让它保持草稿状态。我也倾向于对他人的拉取请求抱有同样的期待：如果它是草稿，我就假定作者还没准备好接受评审。如果它被标记为已就绪待评审，我就假定只差获得足够多的批准，他们就能部署这个拉取请求了。

草稿状态意味着一个拉取请求尚未完成，所以在解决合并冲突或处理评审者反馈时，我会把拉取请求移回草稿。如果我必须改动代码，我会先把我的拉取请求标记为草稿，以免让已经评审过它的人不堪重负。当我把它移回「就绪」时，它会向那些评审者发送一条 GitHub 通知，让他们能再看一遍。

### 保持谦和

「用蜂蜜比用醋能捉到更多苍蝇」这句谚语浮现在我脑海中。我希望自己的拉取请求得到评审，所以我喜欢回复拉取请求上的评论——尤其是我不同意评审者的时候。即使我某条评审评论没写回复，我也常常会用 👍 表达我同意，或用 ❤ 表达感谢。

我希望评审者相信他们的建议不会被遗忘，所以我通过评论让他们保持知情。如果我同意他们的建议——比如进一步重构既有代码——我可能会一边这么说，一边就「在当前拉取请求里做这个改动」提出不同意见。当我在后续的拉取请求里处理他们的反馈时，我会回来提供一个链接，让评审者知道他们的反馈没有被置若罔闻。

在后续实现所建议改动的拉取请求里，我也会标记他们，并附上一条说明：「这处理了 @某某 在 <先前拉取请求 URL> 中提出的反馈。」这既为其他读者提供了上下文，也相当于对原评审者的一次点名致意，把这份功劳归给他们。

当你兑现「在后续分支里处理反馈」的承诺时，这有助于与你的评审者建立信任，从而让他们在批准你未来的拉取请求时更放心，因为他们知道你不会留下一件半成品。

## 结语

代码评审对产品质量的重要性怎么强调都不过分，尤其是在 AI 生成代码的时代。在我的职业生涯中，有很多次仅仅因为多了那第二双眼睛，就逮住了一个缺陷或避免了一起事故。代码评审非常值得投入时间，无论是花在日常评审上、在理顺流程上，还是在构建支持它的自动化上。对开发者来说，现在彻底评审拉取请求，比日后去处理一个已经交付到生产环境的问题，要更快、也更少痛苦。

感谢你对代码质量如此在意，以至于读完了我关于代码评审的理念。你最近查看过你的评审队列吗？也许现在正是把这些想法付诸行动的好时机。

如果你想进一步了解如何在 GitHub 上使用拉取请求评审，请查看 GitHub Community 上由 Staff DevOps Architect Mickey Gousset 和 Staff DevOps Architect Joshua Johanning 撰写的文章，讨论《评审拉取请求的 5 个技巧》。

## 要点回顾

- 代码评审是产品的第二双眼睛：多一个人复核，往往能在问题上线前逮住缺陷或避免事故。
- 好的评审重在清晰：讲明哪些是个人偏好、哪些是批准阻塞项，并给出可参照的示例（最好来自同一仓库）。
- 先提问、再肯定：通过提问检验作者对数据形状、资源占用与性能的假设，并对认同之处明确表达肯定。
- 警惕偏见：资历或熟悉感会让人掉以轻心，用自动化测试和「不懂就问」来抵消主观偏差。
- 慎重使用批准权：「请求修改」是重手段，仅在有紧迫安全问题等少数情况下才用；按现状不破坏生产环境的改动可带评论批准。
- 先自查再求评：提交前对自己的拉取请求做一遍行内自评，也有助于判断是否需要拆小。
- 用草稿状态沟通就绪度：草稿表示未完成，改动代码时先转回草稿，再就绪时通知评审者重新查看。
- 善待评审者并留下闭环：回复评论、给后续拉取请求补链接，兑现「稍后处理反馈」的承诺，从而积累信任。
