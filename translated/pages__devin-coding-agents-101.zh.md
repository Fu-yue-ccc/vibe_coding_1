指南：编程智能体

Cognition 团队　2025 年 6 月　阅读时长 15 分钟

现在是 2025 年。编程智能体并非魔法，但它们大概是我们所能拥有的最接近魔法的东西。我们注意到，一些工程师——尤其是资深（senior）到主任（staff）级别的工程师——比其他人更快地取得了成功。这里，我们分享一些源自客户与我们自身经验的重要心得。

关于本指南：

## 与产品无关

我们讨论的技巧能帮助你在使用任何编程智能体时都取得成功。

## 讲究战术

我们提供自己最喜欢的一些可落地的建议。

## 面向技术

虽然编程智能体对许多人都有价值，但本指南是怀着为工程师服务的初衷写就的。

开发者工具一直在快速演进。十年前，是自动补全与智能感知（intellisense），能够提示方法名并执行程序化的重构。四年前，是副驾驶（copilot）与 Tab 补全，能够为你写出接下来几行代码。两年前，是生成式聊天机器人，能够辅助你的开发，并为你生成整个文件。今天，则是自主智能体，能够在极少人工干预的情况下，把最初的描述一路推进到最终的拉取请求（PR）。过去两年，我们通过打造 Devin 专注于实现这一愿景。如今，对自主智能体的兴趣正达到新的高度，尤其是在同类产品近期陆续发布之后 [1]。除 Devin 外，近期发布的产品还包括 OpenAI 的 Codex 与 Google 的 Jules。一些本地智能体，如 Cursor 与 Claude Code，可以在并行的多个工作区中运行，从而复现类似的效果。这些智能体可以以多种形态出现，包括 Web 应用、移动应用，以及集成在 Slack、GitHub、Linear、Jira 等流行工具之中。

虽然人类与 AI 助手配对所能取得的成果超过任何单独的 AI，但自主智能体端到端处理任务的能力带来了新层次的多任务处理，把每一位工程师都变成了一名工程管理者。

适应与这些新 AI 同事高效协作需要一些时间。有意思的是，我们观察到资深到主任级别的工程师往往最快接纳并熟练使用这些工具。最终，这些工具会在各个级别的工程工作中变得司空见惯。基于我们的经验与客户反馈，我们希望分享关键洞察与经验教训，帮助每个人成功地将这些工具融入自己的工作流。

## 提示词基础

这些基本准则将帮助你在 2025 年与编程智能体进行高效互动。如果只能记住一件事，至少也要记住这些。

### 说明你希望「怎么做」，而不只是「做什么」

把智能体想象成一位决策并不可靠的初级编程搭档。简单的任务可以直接描述，但对于更复杂的任务，要在一开始就清楚地勾勒出你偏好的做法。提前把整体架构与逻辑提供给智能体，不仅能提高它成功的几率，也能减少你审阅代码的时间，因为你已经熟悉了预期的实现方式。

#### 示例：

与其只说「加上单元测试」，不如指明要测试的功能、找出重要的边界情况，并说明（如果有的话）哪些部分需要打桩模拟（mock）。

### 告诉智能体从哪里入手

想一想如果由你自己处理这个任务，你会从哪里开始。即便你不知道具体的文件或函数名，也要提到代码仓库、相关文档以及涉及的关键组件。清楚地指出这些要素，能最大程度减少无用功与困惑。

#### 示例：

「请为我们的代码加上对 Google 模型的支持。你应该查看最新的文档 [见此处](link)，并在 model groups 目录下创建一个新的实现文件」

### 练习防御性提示

想象一下把同样的提示词交给一位新来的实习生。哪里最可能出现困惑或错误？预判这些点，主动澄清你的指令，避免含糊不清。

#### 示例：

「请修复我们搜索模块的 C++ 绑定，使其通过新的单元测试。请注意，你很可能每次修改代码后都需要先重新编译这些绑定，再进行测试。」

### 提供对 CI、测试、类型与静态检查工具的访问

智能体的大部分「魔力」来自它们修正自身错误、并针对报错信息反复迭代的能力。通过类型检查器、静态检查（lint）工具与单元测试等工具提供强有力的反馈闭环，能大幅提升它们的能力。考虑使用带类型的 Python 而不是纯 Python，或使用 TypeScript 而不是 JavaScript。教会你的智能体如何运行常见的检查与测试，确保它拥有全部必要的软件包与访问权限。如果智能体能够与浏览器交互，请给出运行你的前端开发环境的清晰指令。

#### 示例：

我们团队从主要是无类型的 Python SDK 转向了全部使用带类型的 SDK（这本身也是一项很适合交给编程智能体的任务）。

### 发挥你的专业能力

当你熟悉自己的代码库时，上述一切都会变得更容易。即便是简单的任务，也受益于你验证逻辑与结果的能力。人类监督依然不可或缺——最终，你要为代码的最终正确性负责。即便这些工具日益精进，所有权与验证仍将是人类工程师的关键职责。

## 在工作流中使用智能体

一旦你掌握了与智能体对话的基础，就该把这些 AI 帮手引入你的日常工作流了。以下是一些把智能体变成你日常习惯一部分的实用方法：

### 立即承担新任务

想象一位同事给你发消息：「嘿，我们能快速把 X 做出来吗？」或者「我们需要调整一下 Y。」与其让它打断你的节奏，不如快速给自主智能体发一条提示词，让它去调查或完成这个改动。这样你就能腾出手来，继续专注于主要任务。有个有趣的副项目想法？需要快速做原型、抓取数据，或者复现某项研究？交给你的智能体，稍后再回来看结果。

#### 示例：

许多团队在 Slack 上讨论缺陷修复或小的功能更新时，直接 @Devin。

### 随时随地写代码

设想你正在通勤或旅行，这时突然冒出一个紧急缺陷，或者你意识到代码里可能留了个错误。别担心！自主智能体通常支持移动端访问，让你能立刻处理这些问题。无论是通过 Slack 的移动应用，还是专门的移动应用，许多智能体都能让你在路上解决问题，哪怕 Wi-Fi 信号很差。

#### 示例：

拥有这种可选性，让我们团队本身在乘车与飞行途中效率高了很多。

### 把杂活交出去

卡在为了找旧提交而做二分查找（bisect），或者为新功能更新文档上？把这些重复性任务交给你的智能体。你能省下宝贵的时间，并专注于更有创造性、更有影响力的工作。

#### 示例：

在我们团队，工程师发布一个改动后，让智能体更新所有相关文档与面向用户的文案，是很常见的做法。

### 跳过分析瘫痪

在纠结某次重构是否真能简化代码？在两个架构方案之间无法取舍？让你的智能体把两个方案都实现出来。有了具体的例子可供比较，决策就变得简单直接，而且舍弃一个方案也不会伤害任何人的感情。

#### 示例：

在为文本框在 Lexical 与 Slate 之间做选择时，我们让智能体各自实现了一遍。最终 Slate 胜出，交付了更好的结果。

### 搭建预览部署

把你的持续集成/持续交付（CI/CD）流水线设置为每来一个新的拉取请求（PR）就自动创建预览部署，为你提供一个即时的线上 URL。这在评审 AI 智能体完成的前端任务时尤其好用。

#### 示例：

Vercel 是一个部署平台，能让预览部署变得超级简单。

## 委派更大的工单

随着你的拉取请求（PR）在规模与复杂度上超出仅几个文件，一次性处理它们会变得困难。然而，掌握如何委派中大型任务（通常是 1–6 小时的工作量），正是自主智能体带来最高投资回报（ROI）的地方。你不是只省下几分钟，而是能重新夺回数小时的生产力。小任务也许能毫不费力地完成，但把智能体的能力延伸到更大的任务上才会带来最大的回报。

### 自动化你的初稿

对于体量可观的任务，用自主智能体为你的 PR 生成一份初稿，可以启动进展并大幅削减你的工作量。此处成功的关键在于提前清晰地传达你想要的做法。把你自己想象成指导初级开发者的架构师。清晰、详细的指令有助于避免把不必要的时间花在纠正智能体代码中的根本性误解上。

| 领域 | 起草 | 精修 |
|---|---|---|
| 新闻业 | 记者收集初始信息，写出文章初稿 | 编辑审阅稿件、核查事实、润色并定稿以便发布。 |
| 餐饮 | 流水线厨师准备食材、制作初步菜品。 | 副主厨加入调味并调整菜品口味，再送到食客面前。 |
| 编程 | 自主智能体根据初始计划开始任务，产出第一版方案 | 人类开发者审阅草稿 PR，给出反馈，并在合并前进行手动精修 |

🛑 请记住，大型任务（目前）还不是完全无需动手的。对于更具挑战性的任务，要预期会有多轮反馈循环，并预料到需要一些手动精修来打磨。一个现实的目标是节省约 80% 的时间，而非完全自动化；你的专业能力对于验证与最终质量保证依然至关重要。

### 共同制定 PRD

对于复杂或定义模糊的任务，与你的自主智能体协作制定一份详尽的计划可能非常有效。如果你一开始并不了解每一个细节或需求，这完全没关系。先提示你的智能体去探索一些发现性问题，比如「我们的认证系统是如何运作的？」或者「哪些服务可能会受影响？」你也可以让智能体找出具体的相关代码目标，供你尽早确认。

某些智能体，例如 Devin 与 Claude Code，提供专门的规划模式，专注于阅读和探索已有代码，而不是立刻修改它。如果你希望在委派任务前做更深入的准备，像 deepwiki.com 与 Devin Search 这样的专业代码库搜索工具可以迅速为你提供代码库洞察，帮助简化流程。

### 设置检查点

对于多部分任务，尤其是涉及多个代码库的任务，要在途中设立清晰的检查点：

计划 → 实现一个分块 → 测试 → 修复 → 检查点评审 → 下一个分块

明确要求在每一个重要阶段之后暂停，尤其是对于跨多个层次（例如数据库、后端、前端）构建的复杂功能。利用这些检查点来确保实现符合你的预期、澄清疑问（例如「解释一下认证流程并确认它的安全性」），并尽早纠正方向，以免问题层层累积。

#### 示例：

「我想让你实现这个功能，它会横跨我们的数据库、后端与多个前端界面。请先规划所需的数据库模式（schema）变更，完成后告诉我，以便我执行迁移。」→「现在请实现后端改动并加上测试，确保 XYZ 能正常工作。完成后告诉我」→「现在在 Web 与移动端两个界面中实现改动，去调用新的后端端点」

### 教会它验证自己的工作

在给出反馈时，不要只是指出问题（「这个函数不工作」）。清楚地说明你的测试流程，让智能体能够独立验证未来的任务。对于你会频繁重复的测试模式，把它们整合进智能体的永久知识库（见 添加到智能体的知识库 ）。

#### 示例：

在 Devin 中，我们主动提示用户把关键的测试流程保存到智能体的长期记忆中，从而简化未来的交互。

### 提高 AI 热点区域的测试覆盖

目前，智能体还不能完全交互式地彻底测试所有场景。在 AI 大量修改的区域提高测试覆盖，能让你对智能体的产出更有信心。扎实的测试意味着看起来正确的代码可以放心合并，无需担忧。

#### 示例：

我们团队在把实现从 Python 翻译成 C 之前，先加固了代码库中某个关键部分的单元测试。

## 自动化工作流

智能体响应传入事件的速度远快于人类，而且它们比人类同事更愿意做枯燥、重复的工作。

### 为你最重复的工作创建快捷方式

工程团队经常遇到重复性的日常任务。这些正是用智能体自动化的绝佳候选。常见的例子包括：

- 移除功能开关（feature flag）
- 依赖升级
- 为新功能的 PR 修复并补充测试

为了高效地建立这套机制，通常由一位有经验的工程师创建一个健壮、可复用的提示词模板 [2]。在 Devin 中，这类模板被称为 playbook，可以针对这些场景反复运行。

#### 示例：

我们的一位客户在开发新功能时，会自动触发三个专门编写单元测试的智能体。

### 智能代码评审与规则执行

虽然已有专为快速代码评审设计的工具 [3]，但自主智能体也可以是一个有意思的选项，能提供更准确的洞察，尤其是当它们已经为你的代码仓库功能建立了索引时。

#### 示例：

在 Cognition，我们喜欢维护一份工程师最常犯错误的清单，并把它提交到代码库中。然后，与其编写传统的静态检查规则来捕捉这些错误（往往做不到），我们让一个智能体在每一个新 PR 上运行，检查这些错误。

### 接入事故与告警

你也可以设置自主智能体，让它们针对特定事件自动触发。例如，Devin 提供了易于使用的 API，其他智能体则可以通过 CLI 命令集成到自定义工作流中。这些设置在与 MCP 配合、用于摄取第三方错误日志时尤其有效。

⚠️ 在生产服务中分诊问题时，AI 的调试能力并不怎么出色。与其让 AI 端到端地修复随时冒出的缺陷，通常更实际的做法是让 AI 只标出最可疑的错误、改动等。

## 定制与提升表现

### 环境搭建

没有什么比不完整或不匹配的环境更拖慢智能体的了。为了让一切顺畅运行，要让智能体的设置与你的团队完全一致。这包括语言版本、包依赖与自动化检查。例如，pre-commit 应当安装在智能体环境中，而环境配置（密钥、语言版本、虚拟环境、浏览器登录）应当借助 .envrc 或 .bashrc 的自定义配置自动加载。

#### 示例：

我们把智能体的浏览器配置为已预先通过认证的登录状态，省去了手动认证的麻烦，让测试容易得多。

### 构建自定义 CLI 工具与 MCP

MCP 已广泛可用，把智能体连接到外部工具的设置与试验都很快 [4]。在 Devin 中，MCP 仍处于 beta 阶段，因为我们还在摸索支持它们的最佳方式。如需使用请联系我们！但许多人忽略了为智能体设置简单的 CLI 脚本。举个简单的例子，你可以给智能体一个脚本，以便根据工单 ID 拉取 Linear 工单的信息。你可能还想给智能体一个工具，让它可靠地执行工作流的常见部分，比如一个重启本地开发环境的脚本。

#### 示例：

我们有一位客户，通过创建一个 CLI 工具只暴露测试套件中第一个失败的测试，取得了很大成功。该 CLI 提示智能体只关注那一个测试并附上详细错误信息，从而让智能体在长任务上取得更高成功率与更快完成速度。

### 添加到智能体的知识库

如果你的智能体犯了一些常见的错误，那就是把你的反馈固化为智能体知识库的好时机。在 Devin 中，有专门的知识管理系统。许多产品提供 .rules 文件、.md 文件，供智能体永久摄取。不要只给它关于你所用框架的准则，还要告诉它你项目的整体架构。告诉它不同类别的任务通常适用哪种测试、如何运行重要命令，以及你推荐使用哪些工具。

我们让智能体了解在新增一条服务路由时应当遵循的具体流程。这些信息包含它需要在前端与后端添加样板代码的每一处位置。结果是，这些任务现在能轻松委派给我们的 AI。

## 自主智能体的局限

### 调试能力有限

缺陷报告可能看起来简单得具有欺骗性。但许多缺陷往往不仅需要访问数据库与日志，还需要比当今多数 AI 智能体更高水平的调试能力。如果用 AI 辅助调试，我们建议让它给出一份可能的根本原因清单，而不是试图自己去调试并修复一切。然后，人类可以基于自身经验判断哪一个才是真正的根本原因。但一旦原因已知，智能体在实现修复上仍能相当有帮助。

### 细粒度视觉推理能力差

总体而言，当今的模型在匹配设计截图或 Figma 原型所需的细节层面，视觉推理能力并不出色。它们在最能以代码层面描述的视觉内容上最为可靠（例如把 Figma 的代码交给它）。如果你希望它匹配你的视觉风格，应当使用带有可复用组件的好设计系统。

### 知识截止

每当你要使用一个新库时，都应明确地把它指向最新的文档。否则，由于预训练基础模型存在知识截止，多数智能体会沿用这些库的旧有模式。好的智能体在你把它指向文档后能克服这一点，但你必须留意这件事（记住，智能体甚至不知道这些库有了新版本）。

## 管理时间与减少损失

并非每次使用智能体都会成功。在 2025 年，这些智能体的结果确实存在相当大的方差。工作的一部分就是学会以某种方式使用智能体，从而最大化遇到成功结果的机会，同时最小化浪费的时间与 Token。

### 愿意更早止损

使用智能体的新手常犯的一个错误是：即使智能体的工作已经偏离轨道，他们仍坚持要让这次交互成功。如果你发现自己心想「它无视了我的指令」或「这东西在兜圈子」，那你就该果断终止这段对话或手动接管。继续发消息更可能表明你的任务本身复杂度超出了智能体的能力，而不是某个可以纠正的简单失误。

### 让你的实验多样化

如果你刚开始使用智能体，我们建议一开始就分散下注。尝试一系列不同的提示词与想法。在那些你看到智能体天然表现良好的任务类型上加大投入——在它们表现不佳的类型上果断止损。不必觉得非要逼着你的智能体每次都成功。

### 没有进展时就重新开始

在智能体身上，「推倒重来」是正确的答案，其频率远高于对人类。如果你给了一个智能体任务，而它迟迟无法处理反馈或纠正方向，那么换一个全新的智能体、把所有指令一次性前置地说清楚，往往能更快取得成功。智能体纠正一个搞乱的环境的能力，远不如它从头写出全新代码的能力。

## 安全与权限

### 为你的智能体创建账号

一次性邮箱对安全地测试网站很有帮助。如果你的智能体需要访问云资源，为它创建自定义的 IAM 角色。

### 给它一个开发/预发环境

理想情况下，智能体使用与你团队工程师相同的测试配置。我们建议完全避免给它访问生产服务的权限。使用远程智能体时，你可以在智能体的远程机器上运行完全隔离的测试环境。

### 只读 API 密钥

在可能的情况下，给它只读访问权限。我们发现，让人类手动运行任何与外部服务交互的脚本仍然是有帮助的。

## 前方巨变

我们坚信软件工程师不会消失。即便编程智能体变得更聪明、更有能力，深厚的技术专长与对代码库的透彻了解依然无可替代。对你的项目、系统与代码的真正所有权，如今比以往任何时候都更为关键。在我们团队，工程师被期望同时照看多个系统，同时保持深入的理解与审慎的判断。当自动化放大你的影响力时，并行处理多项任务的能力将不只是「可能」，而会成为必备。我们很高兴分享在让我们自己的组织为这一转变做好准备的过程中所积累的洞察，让你和你的团队也能在不断演进的软件开发世界中蓬勃发展。

## 要点回顾

- 2025 年的编程智能体已能端到端处理任务，把工程师变成工程管理者；资深到主任级工程师往往上手最快。
- 提示词要从一开始就说明「怎么做」：给出架构与入手点、预判歧义，并把 CI、类型检查、静态检查与测试的访问权交给智能体。
- 把智能体融入日常：立刻接管新任务、支持移动端处理、把重复杂活交出去、用双实现对比来破除分析瘫痪。
- 委派 1–6 小时级的中大型任务回报最高，但需要共同制定 PRD、设置检查点，并以约 80% 的时间节省（而非完全自动化）为现实目标。
- 通过可复用提示词模板（Devin 中的 playbook）、智能体版代码评审，以及接入事故告警来自动化工作流；生产分诊只让 AI 标出可疑项。
- 定制化重点在环境一致、自定义 CLI 工具与 MCP，以及把反复出现的错误固化进智能体知识库。
- 已知局限：调试能力有限、细粒度视觉推理差、以及预训练知识截止——用新库时务必直接把文档指给它。
- 流程与心理纪律同样重要：尽早止损、多样化尝试、卡住时果断重开；并为智能体单独建账号、只给开发/预发环境与只读密钥。
