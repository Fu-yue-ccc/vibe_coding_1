## 什么是 SAST？

静态应用安全测试（SAST）是一种白盒安全测试方法。SAST 使用应用的静态源代码或二进制文件来识别漏洞。这意味着 SAST 工具在应用未运行时对其代码进行分析。

开发者使用 SAST 检测多种安全风险，例如：跨站脚本（XSS）、不安全的反序列化、缓冲区溢出，以及代码中的其他 OWASP 漏洞。由于仅靠 SAST 无法识别特定于运行时的漏洞，开发者往往必须将 SAST 与其他测试方法结合，才能实现全面的安全。

SAST 是软件开发生命周期的重要组成部分，因为它能及早发现漏洞。你越早发现漏洞，修复成本就越低。由于 SAST 工具可以在开发阶段执行，开发者如今能够在产品上市前对代码进行上千次（！！）编写与测试。

SAST 可以集成到 CI/CD 流水线中，这样使用时被称为「安全 DevOps」或「DevSecOps」。SAST 通过自动化具备很强的可扩展性。能够实现覆盖 SAST 技术的自动化测试，使其成为快速应对代码级风险的高效方案。

## 什么是 DAST？

动态应用安全测试是一种黑盒测试方法。DAST 中的「动态」一词表明，该方法在应用运行时评估其安全性。与 SAST 不同，DAST 不需要访问应用的源代码。取而代之，它会：

模拟外部攻击者的行为。

从外部测试应用，以识别仅在运行时才出现的漏洞。

DAST 能够识别多种安全缺陷，例如拒绝服务（DoS）漏洞和不安全的服务器配置。通过模拟真实世界的攻击场景，DAST 工具评估应用如何响应这些模拟威胁。借助这种方法，开发者可以找出 SAST 等静态测试方法可能遗漏的弱点。

通常，开发者在软件开发生命周期的后期阶段执行 DAST，往往就在部署之前。通过在真实环境中测试应用，DAST 提供对运行时安全的清晰概览，并支撑性能更好、更能抵御潜在攻击的应用。

## SAST 如何工作？

开发者使用 SAST 工具，应用预定义规则与其他检测方法——例如模式匹配与数据流分析——来识别编码错误和其他漏洞。他们将这些工具集成到 IDE 或 CI/CD 流水线中，在编码与测试阶段自动执行扫描。

### 常见 SAST 方法

以下是 SAST 中使用的一些方法。

模式匹配会扫描代码库，查找已知的不安全编码实践模式。例如使用弱加密算法或不安全的 API 调用。

数据流（data flow）跟踪数据如何在应用中流动。它通过追踪不受信任输入流向敏感操作的路径，可以识别 SQL 注入或缓冲区溢出等漏洞。

控制流分析可以分析应用的控制结构。例如循环与条件判断，以发现逻辑缺陷或竞态条件等潜在漏洞。

自定义规则创建。许多工具允许开发者创建自定义规则以贯彻编码最佳实践。以下是这些自定义规则的一些示例：

标记任何在 SQL 查询中使用未净化输入的行为。

识别将用户提供的数据输出到浏览器却未进行适当转义的代码。

高亮使用存在漏洞或已弃用函数的情况，例如 JavaScript 中的 `eval()` 或 C 中的 `strcpy()`。

检测源代码中硬编码 API 密钥与密码的出现，并标记任何缺少对用户提供数据进行输入校验的实例。

依赖项扫描。一些 SAST 工具会分析应用中使用的第三方库与框架，以识别依赖项中的漏洞。

语义分析。通过解读代码的含义而非仅其结构，SAST 工具可以检测不安全的配置或 API 的误用。

机器学习模型：高级 SAST 工具引入机器学习算法，通过分析大型数据集中的模式来识别此前未知的漏洞。

### 使用 SAST 工具时的性能考量

SAST 工具通常需要大量 CPU 与内存资源。在分析大型代码库时，这可能成为主要问题。对一百万行代码进行完整扫描可能消耗数 GB 的 RAM。

SAST 扫描所需时间会因代码库规模而大幅变化，从小型项目的几分钟到企业级应用的数小时不等。这可能影响：

构建流水线的时间线

开发者生产力

考虑使用支持增量扫描的现代 SAST 工具，这样你只需分析变更的代码，而非整个代码库。

此外，通过规则选择与范围界定进行性能调优至关重要。配置不当的 SAST 工具会不必要地分析非关键代码路径，白白浪费时间与资源，却不带来安全收益。

## DAST 如何工作？

DAST 工具模拟真实世界的攻击——例如向输入字段发送各种形式的恶意数据，以观察应用如何处理它们——从而识别应用行为与响应中的漏洞和弱点。

### DAST 的步骤

该过程通常包含以下步骤。

第 1 步：扫描。扫描 Web 应用以发现入口点（如 URL、表单和 API）。该步骤勾勒出应用结构并识别潜在的攻击面。

第 2 步：攻击模拟。通过向应用发送精心构造的请求来模拟恶意活动。这些请求通过尝试利用入口点来测试跨站脚本和跨站请求伪造等漏洞。

第 3 步：漏洞检测。分析应用的响应以识别安全弱点。它会评估应用在遭受攻击时是否按预期运行。例如，可以注入恶意数据来检测 SQL 注入缺陷。

第 4 步：报告。生成包含已检测漏洞与修复建议的报告。开发者可以使用报告中的结果来修复已识别的问题。

现代 DAST 解决方案可以引入 AI 驱动分析与实时数据集成等高级功能。它们会自动创建测试集。动态适应应用结构，并利用机器学习算法将误报降到最低。

### 使用 DAST 工具时的性能考量

以下是使用 DAST 工具时你需要留意的若干性能瓶颈。

DAST 工具会主动与运行中的应用交互，从而临时提高应用服务器与 Web 服务器的 CPU 与内存占用。

DAST 扫描期间产生的大量并发请求会消耗可观的网络带宽。

DAST 扫描器常通过生成唯一请求来绕过或使应用缓存失效，从而降低缓存机制的有效性。

DAST 工具创建与管理多个测试会话，会增加应用服务器的内存占用。

为避免此类问题或尽可能减轻其影响，请遵循以下做法。

将 DAST 扫描安排在应用使用量最少的非高峰时段。

在与生产环境一致的预发布或生产前置环境中进行扫描。

使用 DAST 工具中的限流（throttling）功能来控制并发请求数量。

在扫描期间增加应用服务器的线程池。

为 DAST 扫描器 IP 配置单独的缓存策略。

当超出性能阈值时，实施自动暂停扫描。

## SAST 与 DAST：关键差异

下表总结了 SAST 与 DAST 之间的差异。

| 评判维度 | SAST | DAST |
| --- | --- | --- |
| 测试类型 | 白盒测试。可访问源代码，从内到外测试应用。 | 黑盒测试。无法访问源代码，从外部测试应用。 |
| 支持的软件类型 | 支持多种软件类型，包括 Web 应用、Web 服务和胖客户端（thick client）。 | 支持 Web 应用与 Web 服务，但通常不支持其他软件类型。 |
| 在 SDLC 中的阶段 | 在软件开发生命周期早期执行。 | 在 SDLC 后期进行，通常在部署期间或之后。 |
| 检测到的漏洞 | 识别编码缺陷，例如：SQL 注入、跨站脚本（XSS）、缓冲区溢出等。 | 检测运行时问题，例如服务器配置错误、拒绝服务漏洞以及应用层缺陷。 |
| 修复漏洞的成本 | 由于问题在 SDLC 早期被发现，成本较低。 | 由于漏洞发现较晚、常需紧急修复以按期部署，成本更高。 |
| 运行时与环境问题 | 无法检测特定于运行时或与环境相关的漏洞。 | 可以识别仅在运行时出现或因环境因素而出现的漏洞。 |
| 深度与广度 | 对代码级漏洞提供深入洞察。 | 提供应用外部安全风险的宏观视图。 |
| 与工具的集成 | 与 IDE 和 CI/CD 流水线集成，实现自动化静态分析。 | 与 CI/CD 流水线集成，实现持续运行时测试。 |
| 误报与漏报 | 由于深入代码分析，误报几率更高。 | 误报更低，但由于内部可见性有限，漏报风险更高。 |
| 技术依赖性 | 依赖编程语言与框架；需要与工具兼容。 | 不依赖应用框架，因为它们从外部与应用交互。 |

## SAST 与 DAST 的优缺点

### SAST 的优点

在软件开发生命周期早期识别安全漏洞。

分析代码库，包括基础函数与复杂分支。

直接对源代码操作，无需应用运行。

提供实时反馈与全面洞察，例如漏洞的确切位置。

生成可导出的报告，可通过仪表盘进行跟踪。

支持自动化，因此比人工代码评审更快、更高效。

### SAST 的缺点

常产生大量误报。因此可能需要人工复核。

无法识别运行时或环境特有的漏洞，例如配置错误。

需要针对每种编程语言的特定工具，因此维护复杂。

在理解外部库、API 和 REST 端点方面较为吃力。

### DAST 的优点

识别仅在应用执行期间出现的漏洞。

从外部操作，无需访问源代码。这对于测试第三方应用或已编译代码非常有效。

模拟真实攻击场景，并识别 SAST 遗漏的风险。

不依赖应用的编程语言。

评估整个应用与系统。这包括内存消耗、资源使用与第三方接口。

### DAST 的缺点

只关注应用的外层，可能遗漏更深层的漏洞。

在 SDLC 中应用较晚，因此修复更昂贵、更耗时。

会遗漏 SAST 工具通过源代码分析能识别的某些漏洞。举例来说，假设一个 Web 应用使用不安全的随机数生成器（例如 JavaScript 中的 `Math.random()`）来创建会话令牌。DAST 可能遗漏这一缺陷，因为它只测试运行时行为。（但 SAST 可以检测到。）

大型项目和需要并行运行多个应用实例的项目需要定制基础设施，因此资源消耗大。

## 我该在何时使用 SAST 还是 DAST？

SAST 与 DAST 在保障 SDLC 安全方面发挥互补作用。理解何时使用二者有助于实现全面的安全覆盖。

### 何时使用 SAST

在早期开发阶段。开发者使用 SAST 在 SDLC 早期识别 SQL 注入与硬编码凭据等漏洞。通过在部署前发现这些问题，他们降低了修复的成本与复杂度。

例如：某 SAST 工具扫描 Python 代码，标记出源代码中嵌入硬编码 API 密钥的漏洞。开发者重构代码，改用环境变量来安全地存储与获取密钥。

用于代码评审。SAST 集成到版本控制系统中。使开发者可以在提交代码之前先进行扫描。这确保只有安全的代码进入代码仓库。

示例：某 SAST 工具可以检测出这样一个漏洞：文件路径直接由用户输入构造且未经校验，使应用暴露于路径遍历攻击。开发者通过净化输入并使用安全的库函数来处理文件路径，从而修复该问题。

在持续集成/持续交付流水线中。SAST 在 CI/CD 过程中运行自动化扫描。它向开发者提供实时反馈。

### 何时使用 DAST

生产前测试。开发者使用 DAST 在预发布或 QA 环境中识别运行时漏洞（例如：不安全的配置、认证缺陷、访问控制不足）。

示例：某 DAST 工具可以检测出暴露敏感数据的数据库配置错误。随后开发者可以在部署前加固配置。

部署后监控。DAST 工具持续扫描已部署的应用，以发现由环境变化或新出现威胁所导致的漏洞。这确保应用长期保持安全。

测试第三方集成。DAST 可以模拟外部攻击者的视角，以识别第三方 API 或互联系统中的漏洞。

例如：某 DAST 工具测试一个 Web 应用，发现第三方支付 API 中存在一个漏洞：信用卡详情通过未加密的 HTTP 连接传输。开发者通过为所有 API 通信强制使用 HTTPS 来解决问题。

## 哪一个更有效：SAST 还是 DAST？

SAST 或 DAST 的有效性取决于：

SDLC 阶段

所要应对的漏洞类型

SAST 在早期开发阶段效果最好，主要用于识别源代码中的漏洞、降低成本并推广安全编码实践。相比之下，DAST 聚焦于预发布或已部署应用中的运行时漏洞。它提供对配置错误和不安全集成等问题的洞察。

### 采用混合方法

与其二选一，不如将 SAST 与 DAST 结合，形成多层安全策略，同时应对静态代码与运行时环境中的漏洞。SAST 可以集成到早期开发阶段，在应用编译之前检测并修复代码级问题。一旦应用在测试环境中运行，DAST 就能识别运行时漏洞并评估应用在攻击条件下的行为。

在 CI/CD 流水线中自动化 SAST 与 DAST 扫描，可提供持续反馈并加速开发过程，同时不牺牲安全。

对于敏捷或 DevOps 环境，加入 IAST 或 RASP 等工具可以进一步增强安全。通过关联 SAST 与 DAST 的结果，组织可以实现更全面、更有效的漏洞管理。

### 用 RASP 作为 SAST 与 DAST 的替代方案

运行时应用自我保护（RASP）是一种直接安装在应用所运行服务器上的高级安全解决方案。

RASP 将自身嵌入应用的运行时环境。这种集成使 RASP 能够分析应用的逻辑与数据。在分析过程中，它可以：

在异常行为发生时进行检测。

即时阻断恶意活动。

一个关键区别是，RASP 不只是对潜在问题发出告警——它通过隔离并解决威胁来主动阻止攻击，而不依赖外部工具。

RASP 为 SAST 与 DAST 提供了一种动态替代方案。与分析静态代码的 SAST 和模拟外部攻击的 DAST 不同，RASP 实时运行。它在应用执行期间监控应用行为，并通过终止会话或通知防御者来响应实时威胁。

在保护应用免受绕过网络防御或在开发期间被遗漏的漏洞方面，RASP 尤为有效。

然而，对 RASP 的过度自信可能导致组织忽视安全编码实践。此外，由于 RASP 直接在应用的运行时环境内运行，它可能影响应用性能。RASP 无法替代修复底层缺陷的必要性，但它能在修复进行期间提供持续保护。

正如一位 RASP 用户所评论的：

「是否使用 RASP 工具，应基于对应用具体需求与风险状况的全面评估。」

## 未来：以 SAST、DAST 和 RASP 进行 AppSec 测试

应用测试的未来在于将 SAST、DAST 与 RASP 结合起来，构建全面的安全策略。随着安全挑战日益增长，将这些工具集成到 CI/CD 流水线并自动化其流程将变得不可或缺。

AI 与机器学习方面的进步将提高测试效率，因为它有助于减少误报并改进威胁检测。

### 金融与金融服务业

在金融领域，AI 驱动的工具将改变漏洞被检测与缓解的方式。SAST 与 DAST 将继续在开发与生产前阶段识别编码缺陷与运行时问题。

但不会止步于此：RASP 将借助 AI 更进一步，用于监控实时交易。例如，RASP 可以检测异常模式（例如：攻击者试图实时利用某个漏洞）并在通知安全团队的同时阻断这些活动。

### IoT、边缘与互联设备

在 IoT 方面，这些工具的组合将在保护互联设备方面发挥重要作用。具体如下：

SAST 可以在开发期间确认固件不含漏洞。

DAST 可以测试设备之间通信协议的安全性。

同时，RASP 监控已部署的设备，检测并阻止由新出现威胁导致的未授权访问尝试或数据泄露。

同样，使用多种方法将有助于 IoT 生态系统保持韧性。正如我们众多示例所说明的，SAST、DAST 与 RASP 共同承诺了一个以更强大、更主动的安全措施来构建和部署应用的未来。

## 韧性安全始于主动测试

将 SAST、DAST 与 RASP 结合，可以提供覆盖整个软件开发生命周期的稳健安全。

通过将这些方法集成到 CI/CD 流水线并利用 AI 的进步，组织可以主动应对新出现的威胁。这些方法共同提供了一种整体方法，保护现代应用免受安全漏洞的侵害。

## 要点回顾

- SAST 是白盒静态测试，直接分析源代码或二进制文件，能在开发生命周期早期发现代码级漏洞，修复成本更低，并可集成进 CI/CD（即 DevSecOps）；代价是误报较多、依赖语言特定工具、无法发现运行时问题。
- DAST 是黑盒动态测试，在应用运行时从外部模拟真实攻击者，能发现拒绝服务、不安全服务器配置与运行时缺陷；代价是应用较晚、修复更贵、仅能看到外层。
- 二者并非互斥：SAST 覆盖静态代码、DAST 覆盖运行时环境，将两者的扫描都自动化进 CI/CD 流水线可形成多层防护并保持持续反馈。
- 选择取决于 SDLC 阶段与目标漏洞类型：早期开发以 SAST 为主，生产前置与部署后以 DAST 为主。
- RASP 直接嵌入应用运行时环境，能实时检测异常并即时阻断恶意活动，尤其擅长抵御绕过网络防御的漏洞；但它不能替代修复底层缺陷，且可能影响性能。
- 在多语言、多组件的现代系统中，SAST、DAST 与 RASP 组合使用（敏捷/DevOps 环境还可加入 IAST）才能实现整体覆盖，AI/机器学习将进一步降低误报并提升威胁检测。
- 关键性能要点：SAST 需大量 CPU/内存，宜采用增量扫描；DAST 会推高 CPU、内存与带宽占用并使缓存失效，宜安排在非高峰并做限流。
