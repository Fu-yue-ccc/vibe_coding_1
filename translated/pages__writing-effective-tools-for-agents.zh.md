# 为智能体编写高效的工具——借助智能体之力

发布于 2025 年 9 月 11 日

智能体的效能，取决于我们赋予它的工具。我们分享如何编写高质量的工具与评估，以及如何通过让 Claude 为它自己优化工具来提升表现。

模型上下文协议（MCP）可以让 LLM 智能体获得可能多达数百个工具，用以解决真实世界的任务。但我们如何让这些工具发挥最大效能？

在本文中，我们介绍在一系列智能体式 AI 系统中提升表现的最有效技术¹。

我们首先介绍如何：

- 构建并测试你的工具原型
- 借助智能体为你的工具创建并运行全面的评估
- 与 Claude Code 这样的智能体协作，自动提升工具的表现

最后，我们总结一路走来所识别出的、编写高质量工具的关键原则：

- 选择要实现的工具（以及不要去实现的工具）
- 为工具划分命名空间（namespace），以界定清晰的功能边界
- 从工具向智能体返回有意义的上下文
- 为 Token 效率优化工具响应
- 对工具描述与规格说明做提示工程（prompt engineering）

构建一套评估，可以让你系统地度量工具的表现。你可以用 Claude Code 按照这套评估自动优化你的工具。

## 什么是工具？

在计算领域，确定性系统在给定相同输入时每次都产生相同输出；而非确定性系统——例如智能体——即使在相同的起始条件下也可能给出不同的响应。

传统上写软件时，我们是在确定性系统之间订立一份契约。例如，像 `getWeather("NYC")` 这样的函数调用，每次被调用都会以完全相同的方式获取纽约市的天气。

工具是一类新的软件，它体现的是确定性系统与非确定性智能体之间的契约。当用户问「我今天要带伞吗？」，智能体可能会调用天气工具、凭通用知识作答，甚至先追问一句地点。偶尔，智能体也可能产生幻觉，甚至没能理解该如何使用某个工具。

这意味着在面向智能体编写软件时，我们要从根本上重新思考做法：不要再像为其他开发者或系统编写函数和 API 那样去编写工具与 MCP 服务器，而要为智能体来设计它们。

我们的目标是扩大智能体能够有效发挥作用的「作用面」，让它们借助工具采用多种成功策略去解决各式任务。所幸，据我们的经验，对智能体最「符合工效学」的工具，最终对人来说也出奇地直观。

## 如何编写工具

本节介绍如何与智能体协作，既编写工具、也改进你交给它们的工具。先从快速搭起工具原型并在本地测试开始。接着运行一套全面的评估，以度量后续改动。与智能体并肩工作，你可以反复进行「评估—改进」，直到你的智能体在真实世界任务上取得出色表现。

### 构建原型

在不上手亲自实践的情况下，很难预判哪些工具智能体会觉得好用、哪些不会。先从快速搭起工具原型开始。如果你用 Claude Code 来编写工具（可能一次成型），那么为 Claude 提供工具所依赖的任何软件库、API 或 SDK（可能包括 MCP SDK）的文档会很有帮助。对 LLM 友好的文档通常出现在官方文档站点上的扁平 `llms.txt` 文件中（这是我们 API 的）。

把工具包在本地 MCP 服务器或桌面扩展（DXT）中，就能在 Claude Code 或 Claude Desktop 应用里连接并测试它们。

要把本地 MCP 服务器连接到 Claude Code，运行 `claude mcp add <name> <command> [args...]`。

要把本地 MCP 服务器或 DXT 连接到 Claude Desktop 应用，请分别进入 `Settings > Developer` 或 `Settings > Extensions`。

工具也可以直接传入 Anthropic API 调用，用于程序化测试。

自己动手测试工具，找出其中的粗糙之处。收集用户的反馈，以便对你期望工具支撑的使用场景与提示词建立直觉。

### 运行评估

接下来，你需要通过运行评估来度量 Claude 使用你工具的表现。先从生成大量扎根于真实用途的评估任务开始。我们建议与智能体协作，帮你分析结果并确定如何改进工具。可在我们的工具评估 cookbook 中看到这一流程的端到端演示。

生成评估任务

有了早期原型，Claude Code 可以快速探索你的工具，并创建数十组提示词与响应对。提示词应受真实用途启发，并基于真实的数据源与服务（例如内部知识库与微服务）。我们建议避免过于简单或流于表面的「沙箱」环境，它们无法以足够的复杂度对工具施压。强评估任务可能需要多次工具调用——可能是数十次。

以下是一些强任务的例子：

- 下周与 Jane 安排一场会议，讨论我们最新的 Acme Corp 项目。附上上次项目规划会议的纪要，并预订一间会议室。
- 客户 ID 9182 报告称，他们在一次购买尝试中被收取了三次费用。找出所有相关日志条目，并判断是否还有其他客户受到同一问题影响。
- 客户 Sarah Chen 刚提交了取消请求。准备一份挽留方案。确定：(1) 他们为何要离开，(2) 什么样的挽留方案最有吸引力，(3) 在提出方案前我们应留意的任何风险因素。

以下是一些较弱的任务：

- 下周与 jane@acme.corp 安排一场会议。
- 在支付日志中搜索 `purchase_complete` 与 `customer_id=9182`。
- 按客户 ID 45892 找出取消请求。

每个评估提示词都应与一个可验证的响应或结果配对。你的验证器可以简单到把标准答案与采样响应做精确字符串比对，也可以进阶到请 Claude 来评判响应。避免使用过于严格的验证器，它们会因为格式、标点或合理的替代表述等无关差异而拒掉正确答案。

对于每个提示词—响应对，你还可以可选地指定你期望智能体在解决该任务时调用的工具，以度量智能体在评估中是否成功理解了每个工具的用途。不过，正确解决任务可能存在多条有效路径，因此要尽量避免过度指定或过拟合到某些策略。

运行评估

我们建议用直接的 LLM API 调用以程序化方式运行评估。使用简单的智能体循环（用 `while` 循环包裹交替的 LLM API 调用与工具调用）：每个评估任务一个循环。每个评估智能体应被给予单个任务提示词以及你的工具。

在评估智能体的系统提示词中，我们建议不仅指示智能体输出结构化的响应块（用于验证），还要输出推理与反馈块。指示智能体在工具调用与响应块之前输出这些内容，可能通过触发思维链（CoT）行为来提升 LLM 的有效智能。

如果你用 Claude 运行评估，可以开启交错思考（interleaved thinking）来获得类似的开箱即用能力。这有助于你探查智能体为何调用或不调用某些工具，并凸显工具描述与规格说明中需要改进的具体之处。

除了顶层准确率，我们还建议收集其他指标，如单次工具调用与任务的总运行时长、工具调用总次数、总 Token 消耗以及工具错误。跟踪工具调用有助于揭示智能体常走的常见工作流，并为工具的整合提供机会。

分析结果　智能体是你发现问题的得力伙伴，从相互矛盾的工具描述，到低效的工具实现，再到令人困惑的工具 schema，它们都能提供反馈。不过请记住，智能体在反馈与响应中省略掉的内容，往往比它们写出来的更重要。LLM 并不总是言为心声。

观察你的智能体在哪些地方卡住或困惑。通读评估智能体的推理与反馈（或 CoT），找出粗糙之处。审查原始记录（包括工具调用与工具响应），捕捉智能体 CoT 中未明确描述的任何行为。要读出言外之意；记住你的评估智能体并不必然知道正确答案与策略。

分析你的工具调用指标。大量冗余的工具调用，可能意味着有必要重新调整分页或 Token 上限参数；大量因参数无效而产生的工具错误，可能意味着工具需要更清晰的描述或更好的示例。我们发布 Claude 的网页搜索工具时发现，Claude 会毫无必要地在工具的 `query` 参数后追加 `2025`，使搜索结果产生偏差并降低表现（我们通过改进工具描述把 Claude 引导到了正确方向）。

### 与智能体协作

你甚至可以让智能体来分析你的结果并为你改进工具。只需把评估智能体的记录拼接起来，粘贴进 Claude Code。Claude 擅长分析记录并一次性重构大量工具——例如在新改动发生时确保工具实现与描述保持自洽。

事实上，本文中的大部分建议，都来自我们用 Claude Code 反复优化内部工具实现的过程。我们的评估建立在内部工作区之上，复刻了内部工作流的复杂度，包括真实的项目、文档与消息。

我们依靠留出测试集来确保没有对「训练」评估过拟合。这些测试集表明，我们还能取得超出「专家」工具实现所达到水平的额外性能提升——无论这些工具是由我们的研究员手工编写，还是由 Claude 自己生成。

## 编写高效工具的原则

本节中，我们把所学提炼为几条编写高效工具的指导原则。

### 为智能体选择合适的工具

工具更多并不总带来更好的结果。我们观察到的一个常见错误是：工具仅仅把现有的软件功能或 API 端点包了一层——而不论这些工具是否适合智能体。这是因为，智能体相对于传统软件有其独特的「可供性」——也就是说，它们感知自己能借助这些工具采取哪些潜在行动的方式是不同的。

LLM 智能体的「上下文」是有限的（即它们一次能处理的信息量有上限），而计算机内存既便宜又充裕。试想在一本通讯录里查找某个联系人。传统软件程序可以高效地存储并逐个处理联系人列表，检查完一个再继续下一个。

然而，如果 LLM 智能体使用一个会返回全部联系人的工具，然后不得不逐 Token 通读每一个联系人，那它就是在把有限的上下文空间浪费在无关信息上（想象你从头到尾逐页翻阅通讯录来查找一个联系人——也就是暴力搜索）。更好也更自然的做法（对智能体和人都是如此）是先跳到相关的那一页（也许按字母顺序找到它）。

我们建议围绕少数几个高影响力的具体工作流构建少量经过深思熟虑的工具，使之与你的评估任务相匹配，再由此逐步扩展。在通讯录的例子中，你或许会选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts` 工具。

工具可以整合功能，在底层处理可能多个离散的操作（或 API 调用）。例如，工具可以用相关元数据充实工具响应，或在单次工具调用中处理经常串联的多步任务。

以下是一些例子：

- 与其实现 `list_users`、`list_events` 和 `create_event` 三个工具，不如考虑实现一个 `schedule_event` 工具，它查找空闲时间并安排一场活动。
- 与其实现 `read_logs` 工具，不如考虑实现一个 `search_logs` 工具，它只返回相关的日志行以及一些周边上下文。
- 与其实现 `get_customer_by_id`、`list_transactions` 和 `list_notes` 三个工具，不如实现一个 `get_customer_context` 工具，一次性汇总某位客户全部近期且相关的信息。

确保你构建的每个工具都有清晰、独特的目的。工具应使智能体能够以与人类大致相同的方式细分并解决任务——前提是能访问相同的底层资源——同时减少原本会被中间输出消耗掉的上下文。

工具过多或彼此重叠，也可能分散智能体追求高效策略的注意力。对你构建（或不构建）哪些工具进行审慎而有选择的规划，真的会带来回报。

### 为工具划分命名空间

你的 AI 智能体有可能接触到数十个 MCP 服务器和数百个不同的工具——包括其他开发者提供的工具。当工具在功能上重叠或用途模糊时，智能体会搞不清该用哪一个。

命名空间（把相关工具归组到共同前缀之下）有助于在大量工具之间划出边界；MCP 客户端有时会默认这样做。例如，按服务为工具划分命名空间（如 `asana_search`、`jira_search`），并按资源划分（如 `asana_projects_search`、`asana_users_search`），可以帮助智能体在恰当的时机选到恰当的工具。

我们发现，在前缀式与后缀式命名空间之间做选择，会对我们的工具使用评估产生不小的影响。影响因 LLM 而异，我们建议你根据自己的评估来选择命名方案。

智能体可能会调错工具、用错的参数调用对的工具、调用过少的工具，或者错误地处理工具响应。通过有选择地实现那些名称反映任务自然细分的工具，你同时减少了加载进智能体上下文的工具与工具描述数量，并把智能体式计算从智能体的上下文卸载回工具调用本身。这降低了智能体犯错的整体风险。

### 从工具返回有意义的上下文

同理，工具实现应留意只向智能体返回高信噪比的信息。它们应优先考虑上下文相关性而非灵活性，并避开底层技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。像 `name`、`image_url` 和 `file_type` 这样的字段，更有可能直接为智能体后续的行动与响应提供信息。

智能体在处理自然语言的名称、术语或标识符时，也往往比处理晦涩的标识符成功得多。我们发现，仅仅把任意的字母数字 UUID 解析为语义上更有意义、更易解读的语言（甚至只是改为 0 起始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精度。

在某些情况下，智能体可能需要兼具与自然语言和技术标识符输出交互的灵活性，哪怕只是为了触发后续的工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。要做到两者兼得，你可以在工具中暴露一个简单的 `response_format` 枚举参数，让你的智能体控制工具返回的是「简洁」还是「详细」响应（见下方图片）。

### 为 Token 效率优化工具响应

优化上下文的质量很重要，但优化工具响应返回给智能体的上下文数量同样重要。

对于任何可能占用大量上下文的工具响应，我们建议组合使用分页、范围选取、过滤和／或截断，并设置合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 个 Token。我们预计智能体的有效上下文长度会随时间增长，但对上下文高效工具的需求仍将存在。

如果你选择截断响应，务必用有用的指示来引导智能体。你可以直接鼓励智能体采用更省 Token 的策略，比如在知识检索任务中做多次小而精准的搜索，而不是做一次宽泛的大搜索。同样，如果某次工具调用引发错误（例如在输入校验时），你可以对错误响应做提示工程，让它清晰传达具体且可执行的改进建议，而不是给出晦涩的错误码或堆栈回溯。

### 用提示工程打磨工具描述

现在来到提升工具最有效的方法之一：用提示工程打磨你的工具描述与规格说明。由于它们会被加载进智能体上下文，因而能共同把智能体引导向高效的工具调用行为。

在撰写工具描述与规格时，想一想你会如何向团队里新入职的同事描述这个工具。考虑你可能隐含带入的上下文——特殊的查询格式、小众术语的定义、底层资源之间的关系——并把它明确写出来。通过清晰描述（并用严格的数据模型强制执行）预期的输入与输出，避免歧义。尤其是输入参数应命名明确：与其用名为 `user` 的参数，不如用名为 `user_id` 的参数。

借助评估，你可以更有把握地衡量提示工程带来的影响。即便对工具描述做微小改进，也可能带来显著提升。在我们对工具描述做出精确改进之后，Claude Sonnet 3.5 在 SWE-bench Verified 评估上取得了当时最佳的表现，错误率大幅下降、任务完成度提升。

关于工具定义的其他最佳实践，可参见我们的开发者指南。如果你在为 Claude 构建工具，我们还建议阅读工具如何被动态加载进 Claude 系统提示词的相关说明。最后，如果你在为 MCP 服务器编写工具，工具注解（tool annotations）有助于揭示哪些工具需要开放世界访问权限，或会做出破坏性更改。

## 未来展望

要为智能体构建高效的工具，我们需要把软件开发实践从可预测、确定性的模式，重新调整为非确定性的模式。

通过本文描述的这套迭代式、以评估驱动的流程，我们识别出了工具之所以成功的若干一致规律：高效的工具被有意地、清晰地定义，审慎地使用智能体上下文，能够在多样化的工作流中相互组合，并让智能体能够直观地解决真实世界的任务。

未来，我们预期智能体与世界交互的具体机制会持续演进——从 MCP 协议的更新，到底层 LLM 自身的升级。只要以系统化、评估驱动的方式来改进面向智能体的工具，我们就能确保：随着智能体能力增强，它们所用的工具也会随之共同演进。

## 要点回顾

- 工具是智能体与现实世界交互的接口，工具的设计质量直接决定智能体能否可靠完成任务。
- 用智能体来改进工具：让 Claude 基于评估任务自动审视并改写工具的 schema 与描述，形成「撰写—评估—改进」的闭环。
- 工具描述要按「向新同事解释」的标准撰写，明确用途、输入输出、边界情况与错误处理。
- 输入参数的命名与粒度要贴合模型推理习惯：`user_id` 优于 `user`，并避免让模型自行拼接自由文本参数。
- 用命名空间（namespace）区分同类工具以避免名称冲突，例如 `asana_search`、`jira_search`。
- 为 Token 效率优化工具响应：通过分页、范围限定、过滤与截断控制返回体量（Claude Code 默认上限为 25,000 tokens）。
- 当响应被截断或出错时，应给出可执行的下一步指引，而不是只抛出一个错误。
- 把确定性工作交给工具、把非确定性留给模型；交错思考与思维链能提升工具调用的质量。
