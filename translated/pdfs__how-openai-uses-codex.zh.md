## 引言

Codex 每天都被 OpenAI 内众多技术团队使用，包括安全（Security）、产品工程（Product Engineering）、前端（Frontend）、API、基础设施（Infrastructure）与性能工程（Performance Engineering）等团队。团队用它来加速一系列工程任务，从理解复杂系统、重构大型代码库，到交付新功能、在紧张期限内处置事故。

基于对 OpenAI 工程师的访谈与内部使用数据，我们整理了以下用例与最佳实践，展示 Codex 如何帮助我们的团队更快推进、提升工作质量，并在规模上管理复杂性。

## 用例 1：代码理解

在入职、调试或调查事故时，Codex 能帮助我们的团队快速熟悉代码库中陌生的部分。

团队常用 Codex 定位某个功能的核心逻辑、梳理服务或模块之间的依赖关系，并追踪数据在系统中的流转。它还能帮助揭示架构模式，或补全那些原本需要投入大量手工工作才能生成的缺失文档。

在事故响应过程中，Codex 通过揭示组件之间的交互、追踪故障状态如何在系统中扩散，帮助工程师快速进入陌生领域。

### 来自各团队的轶事

> 修 bug 时，我会用 Ask 模式看看代码库里还有哪些地方可能出现同样的问题。
> —— 性能工程师，检索系统团队（Performance Engineer, Retrieval Systems）

> 值班时，我把堆栈跟踪粘给 Codex，问它鉴权流程在哪里。它会直接跳到正确的文件，让我能快速做分诊。
> —— 站点可靠性工程（SRE），API 平台团队（Site Reliability Engineer, API Platform）

> 我在 Terraform 和 Python 上问 Codex「这件事该在哪里做」这类仓库问题，比 grep 快得多。
> —— DevOps 工程师，基础设施服务团队（DevOps Engineer, Infrastructure Services）

试用 Codex 完成代码理解任务时，可用以下示例提示词：

- 这个仓库里鉴权逻辑实现在哪里？
- 总结请求从入口到响应是如何流经这个服务的。
- 哪些模块与 [填入模块名] 交互，失败又是如何处理的？

## 用例 2：重构与迁移

Codex 常用于跨多个文件或包的改动。例如，当工程师更新某个 API、改变某个模式的实现方式，或迁移到新的依赖时，Codex 能让改动被一致地应用。

当同一处更新需要应用到几十个文件时，或者当该更新需要理解那些用正则或查找替换很难捕获的结构与依赖关系时，它尤其有用。

团队也用它来做代码清理：拆分过大的模块、用现代模式替换旧模式，或为了让代码更易测试而做准备。

### 来自各团队的轶事

> Codex 把每一处遗留的 `getUserById()` 都换成了我们的新服务模式，并开了拉取请求（PR）。它几分钟就做完了原本要花几小时的事。
> —— 后端工程师，ChatGPT Web

> 为了清掉发布阻塞项，我让 Codex 扫描旧模式的每一处实例，把影响面总结成 Markdown，然后开带修复的 PR。
> —— 产品工程师，ChatGPT Enterprise

试用 Codex 做重构与迁移时，可用以下示例提示词：

- 把这个文件按关注点拆成多个模块，并为每个模块生成测试。
- 把所有基于回调的数据库访问转换成 async / await。

## 用例 3：性能优化

Codex 用于识别并解决性能瓶颈。

在调优或提升可靠性的工作中，工程师会让 Codex 分析缓慢或内存占用高的代码路径，例如低效的循环、冗余操作或高昂的查询，并给出优化替代方案，通常能带来效率与可靠性上的显著收益。

Codex 也用于支持代码健康度：识别仍在使用中的高风险或已弃用模式。我们的团队依靠它来减少长期技术债，并主动预防回归。

### 来自各团队的轶事

> 我用 Codex 扫描重复的昂贵数据库调用。它很擅长标出热点路径，并起草出我随后可以调优的批量查询。
> —— 基础设施工程师，API 可靠性团队

> Codex 很擅长快速发现性能问题——我花 5 分钟写提示词，省下 30 分钟的工作。
> —— 平台工程师，模型服务团队

试用 Codex 做性能优化时，可用以下示例提示词：

- 针对内存效率优化这个循环，并解释你的版本为什么更快。
- 找出这个请求处理函数中重复的昂贵操作，并给出可缓存的机会。
- 为这个函数建议一种更快的数据库查询批处理方式。

## 用例 4：提升测试覆盖率

Codex 帮助工程师更快地写测试——在覆盖率偏低或完全缺失的地方尤其如此。

在处理 bug 修复或重构时，工程师常让 Codex 给出覆盖边界情况或可能失败路径的测试建议。对于新代码，它能根据函数签名与周边逻辑生成单元测试或集成测试。

Codex 特别擅长识别那些在初始测试中常被遗漏的边界条件，比如空输入、最大长度，或罕见但合法的状态。

### 来自各团队的轶事

> 我把覆盖率低的模块交给 Codex 跑一整晚，早上醒来就有可直接运行的单元测试 PR。
> —— 前端工程师，ChatGPT Desktop

> 切换 monorepo 分支很痛苦时，我就让 Codex 写测试并启动持续集成/持续交付（CI/CD），自己继续在当前分支上工作。
> —— 后端工程师，支付与计费团队（Payments & Billing）

试用 Codex 提升测试覆盖率时，可用以下示例提示词：

- 为这个函数编写单元测试，覆盖边界情况与失败路径。
- 为这个排序工具生成一个基于属性的测试。
- 扩展这个测试文件，覆盖围绕空输入与非法状态的缺失场景。

## 用例 5：提高开发速度

Codex 通过同时加速开发周期的起点与终点，帮助团队更快推进。

在启动新功能时，工程师用它来搭脚手架——生成文件夹、模块与 API 桩代码，从而快速得到可运行的代码，而不必手工把每一块接起来。

当项目临近发布时，Codex 通过处理那些更小但必要的任务来帮助赶上紧张期限，例如对 bug 做分诊、补上最后一公里的实现缺口，以及生成发布推进（rollout）脚本、遥测钩子或配置文件。

它也用于把产品反馈转化为起步代码。工程师常把用户需求或规格说明（spec）粘贴进来，让 Codex 生成一份粗略草稿，之后再回来完善。

### 来自各团队的轶事

> 我整天都在开会，却还是合并了 4 个 PR，因为 Codex 在后台干活。
> —— 产品工程师，ChatGPT Enterprise

> Codex 帮忙完美地交付了 3 到 4 个低优先级修复，这些活儿本来会在待办里烂掉，这让人特别有掌控感。
> —— 全栈工程师，内部工具团队

试用 Codex 提高开发速度时，可用以下示例提示词：

- 为 POST /events 搭建一条新的 API 路由，包含基本的校验与日志。
- 使用这个模板生成一个遥测钩子，用于追踪新引导流程的成功/失败 [填入你的遥测代码示例]。
- 基于这份规格说明创建一个桩实现：[填入规格说明或产品反馈]。

## 用例 6：保持心流

当工程师的日程碎片化、被各种中断填满时，Codex 能帮助他们保持产出。

它被用来记录未完成的工作、把笔记变成可运行的雏形，或把探索性任务分离出去以便日后回来处理。这让暂停与恢复工作更轻松，且不会丢失上下文，对他们值班或会议很多时尤其如此。

### 来自各团队的轶事

> 如果我顺手发现一处该修的地方，我会直接发一个 Codex 任务，而不是去切换分支，等有空时再评审它的 PR。
> —— 后端工程师，ChatGPT API

> 我经常把 Slack 讨论串、Datadog 链路追踪、issue 等等转发给 Codex，这样我就能专注于高优先级的工作。
> —— API 工程师，基础设施可观测性团队

试用 Codex 保持心流时，可用以下示例提示词：

- 生成一份重构这个服务并把它拆成更小模块的计划。
- 把重试逻辑先搭成桩代码并加一个 TODO——退避逻辑我稍后补。
- 总结这个文件，好让我明天能接着上次的进度继续。

## 用例 7：探索与构思

Codex 对开放式工作也很有用，比如寻找替代方案或验证设计决策。你可以让它给出解决问题的不同方式、探索不熟悉的模式，或对假设做压力测试。这有助于揭示取舍、扩展设计选项、并让实现选择更清晰。

它也用于识别相关联的 bug。给定一个已知问题或已弃用的方法，Codex 能在代码其他位置找出相似的模式，从而更容易捕获回归或完成清理工作。

### 来自各团队的轶事

> Codex 帮我解决冷启动问题——我粘贴一份规格说明（spec）和文档，它就搭出代码骨架，或指出我漏了什么。
> —— 产品工程师，ChatGPT Desktop

> 修完一个 bug 后，我会问 Codex 相似的 bug 还可能藏在哪里，然后拆出后续任务。
> —— 性能工程师，检索系统团队

试用 Codex 做探索与构思时，可用以下示例提示词：

- 如果这个系统是事件驱动而非请求/响应式的，它会如何运作？
- 找出所有手工拼接 SQL 字符串、而没有使用我们查询构造器的模块。
- 用更函数式的风格重写这段代码，避免可变状态与副作用。

## 最佳实践

当 Codex 获得结构、上下文以及反复迭代的空间时，它表现最好。以下是 OpenAI 各团队正在养成的一些习惯，用于在日常工作中稳定地从中获得价值。

**从 Ask 模式开始**
对于较大的改动，先用 Ask 模式让 Codex 给出一份实现计划，当你切换到 Code 模式时，这份计划再作为后续提示词的输入。这个两步流程能让 Codex 有据可依，并有助于避免其输出中的错误。Codex 最适合范围界定清晰的任务，即你或同事大约需要一小时完成、或需要实现几百行代码的任务。随着模型进步，可以预期它能承担的任务规模也会变大。

**迭代改进 Codex 的开发环境**
设置启动脚本、环境变量与网络访问，能显著降低 Codex 的出错率。在运行任务的过程中，留意那些可以通过 Codex 环境配置纠正的构建错误。这可能需要几轮迭代，但长期来看会带来显著的效率收益。

**像写 GitHub Issue 一样组织你的提示词**
当提示词的写法与你描述 PR 或 issue 中改动的方式一致时，Codex 的回应会更好。这意味着在相关时提供文件路径、组件名、差异（diff）与文档片段。用诸如「按 [模块 X] 中的做法实现这个」这样的模式来写提示词，能提升效果。

**把 Codex 任务队列当作轻量待办清单**
随手发出任务，用来捕捉支线想法、半成品工作或顺带发现的修复。不必有在一次交互中就产出完整 PR 的压力。Codex 很适合作为暂存区，等你重新进入专注状态时再回来处理。

**用 AGENTS.md 提供持久上下文**
维护一份 AGENTS.md 文件，帮助 Codex 在你的仓库中跨提示词更有效地工作。这类文件通常包含命名规范、业务逻辑、已知怪癖，或 Codex 无法仅凭代码推断出的依赖关系。关于如何组织 AGENTS.md 文件的更多内容，请参阅文档。

**利用「Best of N」改善输出**
Best-of-N 功能让你能针对单个任务同时生成多个回复，从而快速探索多种方案并挑出最好的那个。对于更复杂的任务，你可以审阅若干轮迭代，并组合不同回复的部分内容，得到更强的结果。

## 展望

Codex 仍处于研究预览阶段，但它已经在我们构建软件的方式上产生了真实影响，帮助我们更快推进、写出更好的代码，并承接那些原本永远不会被排上优先级的工作。

我们对前方的潜力感到兴奋——随着我们的模型变得更好、Codex 更深入地融入我们的工作流，我们期待解锁用它开发软件的更多强大方式。我们也会继续分享一路上的所学所得。

### 要点回顾

- Codex 被 OpenAI 的安全、产品工程、前端、API、基础设施、性能工程等团队日常使用，覆盖从理解复杂系统到在紧张期限内处置事故的各类任务。
- 代码理解：定位功能核心逻辑、梳理服务与模块关系、追踪数据流，在入职、调试与事故响应中快速进入陌生领域。
- 重构与迁移：跨数十个文件一致地应用改动，处理正则或查找替换难以覆盖的结构与依赖关系，并做模块拆分等代码清理。
- 性能优化：分析缓慢或内存占用高的代码路径并给出优化替代方案，同时识别仍在使用的已弃用模式以降低技术债。
- 测试与速度：为边界条件与失败路径补测试；用脚手架、桩代码与发布推进脚本加速开发周期两端。
- 保持心流与探索构思：把碎片化时间里的未完成工作、支线想法与探索任务交给任务队列，之后再回来处理。
- 最佳实践：先用 Ask 模式出计划再切 Code 模式实现，迭代改进开发环境，像写 issue 一样写提示词，用 AGENTS.md 提供持久上下文，并善用 Best-of-N。
