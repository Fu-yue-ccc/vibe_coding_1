# 规格说明已死，规格说明万岁！

### 原型是新的规格说明，而规格说明是新的……源代码？

Ravi Mehta 与 Danny Martinez

2025 年 7 月 31 日

在我的职业生涯中，规格说明（spec）变得越来越短。我在微软起步时，衡量一名产品经理（PM）价值的标准是其所写规格说明的重量。多年后，在 Tripadvisor，我们把那位带着一张写在餐巾纸上的规格说明走进产品评审会的 PM 奉为传奇。

产品团队常常把规格说明当作文书工作——在「真正的工作」即发布之前不得不做的麻烦事。工程师因优雅的代码受到褒奖，设计师因精美的用户体验受到褒奖，PM 因交付影响力而获得赞誉。但规格说明呢？它们通常被草草带过、被丢在一边、被遗忘。

这一直是一个错误。在我的《产品能力工具箱》中，「功能规格说明」被置于首位——在十二项能力中排第一——这是有原因的。它与产品交付、产品质量一同构成了产品执行力的基础。

完美的执行是优秀产品管理的根基，而一份出色的规格说明就是起跑线。

如今，我们构建产品的方式正在转变。工程师变得更快了——快得多。AI 能在几分钟内把粗糙的想法变成可运行的代码。瓶颈不再是构建，而是知道要构建什么，并让团队围绕这些需求对齐。

突然间，那份不起眼的规格说明不再是转瞬即逝的文书工作。它成了产品管理的基石——它正在变成源代码本身。

为什么 PM 突然成了瓶颈

在近期题为《用 AI 更快地构建》的演讲中，吴恩达（Andrew Ng）指出了一种前所未有的趋势：

「这是我人生中第一次看到有管理者向我提议，让 PM 的数量达到工程师的两倍。我至今仍不确定这个提议是否明智，但我认为它标志着世界的走向。」——吴恩达

这印证了我们在上一篇文章中的预测：随着工程师借助 AI 以数倍速度交付，公司需要更多 PM 来支撑这些高产的工程师，而不是更少。

随着产品交付加速，产品管理的其他各个方面——理解客户需求、打磨正确的功能、验证影响力——都承受着巨大压力。

而所有这些压力都汇聚到一个产物上——规格说明。

规格说明——新的源代码

在传统软件开发中，程序员编写人类可读的「源代码」，它会被编译成高度优化、机器可读的「目标代码」。「目标代码」（也称为二进制）是一种副产品，可以用源代码重新生成。源代码字面上就是真相之源。

来自 OpenAI 的 Sean Grove 提出了一个颇具挑衅性的论点。在他近期的演讲《新的代码》中，他主张一份写得好的提示词（也就是规格说明）就是新的源代码。

从这个角度看，我们做 AI 开发的方式是反的。我们精心编写提示词，把意图传达给模型。AI 生成代码。然后我们保留代码，把提示词丢掉。

「这感觉就像你把源代码碎掉，然后非常小心地对二进制做版本控制，」Grove 评论道。

想想这一点。在传统编程中，源代码是神圣的。源代码包含注释、结构与文档——理解并修改系统所需的一切。二进制只是一个下游产物。

但在 AI 时代，我们把这个关系颠倒了。我们把生成的代码当作值得保留的产物，而把规格说明——也就是提示词——当作一次性的东西。

Grove 认为这恰好弄反了。代码，哪怕是优雅的代码，也只是他所说的、对规格说明的「有损投影」。正如反编译二进制无法还原本来的注释与变量名，阅读代码也无法告诉你它背后的完整意图。

然而规格说明包含了一切。一份足够健壮的规格说明可以生成「优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客」。

「一份足够健壮的规格说明可以生成优秀的 TypeScript、优秀的 Rust、服务端、客户端、文档、教程、博客文章，甚至播客。」——Sean Grove，OpenAI

更重要的是，规格说明能做代码做不到的事：让人类与机器在共同目标上对齐。Grove 说得简单：「一份书面规格说明能有效地让人对齐，它是你用来沟通、讨论、辩论、引用并达成同步的产物。」

他预测：「在不久的将来，沟通得最有效的人就是最有价值的程序员。而且，字面上说，如果你能有效沟通，你就能编程。」

新的稀缺技能不是写代码，而是写出能充分承载意图与价值的规格说明。

对产品经理而言，这听起来应该很熟悉。这正是我们一直在做的事——只不过现在机器也在听了。

等等，原型不是已经杀死了规格说明吗？

直到不久前，产品生命周期都必须从规格说明（或 PRD、概念文档、餐巾纸）开始，由它启动最初的线框图、设计、原型与 MVP 开发。

传统做法感觉像是不得不承受的麻烦事。工程师构建基础 MVP，好把某些东西——任何东西——交到客户手中。「如果你的产品第一版没有让你感到难堪，说明你发布得太晚了」成了信条。

我们构建产品的整个方法最近发生了重大转变；在这个新世界里，规格说明往往是产出，而不是输入。

今天，你无需写一行代码，就能把原型交到客户手中。v0、Lovable、Replit 这类工具让你在数小时内——而非数周内——构建出可用的原型。无需工程投入。

这不仅更快，而且根本不同。手握一个用 vibe coding（氛围编码）方式做出来的原型，你可以在写下功能规格说明的第一行之前就收集真实的客户反馈。你可以验证假设、迭代流程、打磨交互。

旧的工作流是这样的：模糊的想法 → 线框图 → 设计稿 → 工程师构建的 MVP → 客户反馈 → 痛苦的规格说明修订 → 线框图 → 设计稿 → 重建 → 祈祷。

新的工作流：模糊的想法 → 快速原型 → 客户反馈 → 极其清晰的规格说明 → AI 辅助实现。

原型并没有杀死规格说明。它们正在让规格说明变得更好。

规格驱动开发的实践

让我们看一个实操案例，了解这一切如何落地。Danny Martinez 是 decimals 的创始人，这是一个（仍处于隐身模式的）平台，让创作者经济中的专家把他们人脉中的人才安置到工作岗位。

你是寻找新机会的 AI 优先 PM 吗？把你的信息留给我们，遇到有意思的机会时我们会通知你。

你是一家想招聘 AI 优先 PM 的公司吗？申请加入我们的人才网络，我们会分享一份精选的候选人短名单。

Danny 将带我们走一遍他们的规格驱动开发流程——这个流程带来了两方面影响：

在较大功能上与工程的沟通得到极大改善，以及

让 Danny 尽管此前毫无编程经验，也能在较小的功能上从详细的规格说明一路做到上线功能。

接下来交给 Danny……

这是我最近做的一个例子。背景是：我们正在构建一个产品，让专家型意见领袖能把自己人脉中的候选人安置到工作岗位。在上线一个新的落地页之后，我们需要给专家们一个快速获取自己页面链接的方式。

> 我们需要在页头加一个按钮，指向「公司申请」页面。我现在专注在处理邮件。如果这个你能接过去，它是可以 vibe coding 出来的，拜托了。

这条消息来自我的联合创始人，指的是一个需要上线的小按钮。足够简单，而且恰恰是如今非技术人员也能自己上线的那类事情。

下面是把这件事在几分钟内上线所用的配置与步骤：

- 项目管理工具：Linear
- 集成开发环境（IDE）：VS Code
- 扩展：GitHub Copilot Pro
- 模型：Claude Sonnet 4
- MCP 服务器：Linear MCP server，让 Linear 工单可以通过 Copilot 访问

我们来看看这个流程中的各个步骤（可对照上方的 Loom 视频跟做）：

1. 从联合创始人在 Slack 上的消息生成一个 Linear 工单（00:14）
2. 在上述工单中明确我希望新的文案是什么（00:25）
3. 打开 Copilot，提示 Claude 打开这个 Linear 工单（01:18）
4. 提示 Claude 审阅该工单，并结合代码库进行分析（01:52）
5. 提示 Claude 创建分支并实现这些改动（02:30）
6. 测试改动，确认它们按预期工作。（02:52）
7. 在 GitHub 上开一个拉取请求（PR），把这些改动合入代码库（03:55）
8. 等待工程师评审/批准该 PR

把视角拉远，这套配置的真正威力就清晰起来。是的，这只是一个微不足道的例子，但要点依然成立：一个非技术人员现在可以往来于 Linear 工单、代码库与工程师之间，而这一切只需要通过 GitHub Copilot 给 Claude 几句提示词。

再说一次：这当中关键的并不是代码本身，而是规格说明。

不过，有必要对上述做法加以限定，说明它要运作良好需要什么：

- 具体明确：使用含糊的规格说明只会得到一个混乱的代码库。用 Claude 接手工单的初稿、审阅代码库，并帮助把它写得更具体，是这个流程中不可或缺的一环。在我们的案例里，我们还制定了写好规格说明的准则。
- 有所选择：上述做法用于较简单的任务最理想。工单越复杂，就越需要真正懂行的人参与（在这些情况下，「自助」最终往往根本不是自助）。
- 把关：这种做法之所以运作良好，仅仅是因为有一位真正懂行的工程师在评审改动，并确保简洁性与功能性之间的平衡得到维持。

但我们要说清楚：规则已经变了。规格说明是所有构建产品的人——包括 LLM——的真相之源。

在合适的配置下，非技术人员期望为代码库做贡献完全是现实可行的。只要有足够的时间与耐心，你可以开始理解代码库并自己实现改动，而不是每次都只是依赖 Claude 来救场。

有朝一日，你甚至可能期望在你啜饮咖啡的时候，由一个 AI 智能体把你的工单上线。

如果你是 PM，并担心 AI 会对你的工作做什么，关键在于认识到这份工作本身正在改变。但对其他所有人来说也是如此。好消息是，一名优秀 PM 所需的核心技能在这个新世界里甚至更有价值。

正如我们在上一篇文章中所预测的，以这种方式运作的公司将需要更多而非更少的 PM。而事实证明，这个预测应验得相当不错：

规格说明万岁！

创造「赛博空间」一词的科幻作家威廉·吉布森曾说：

> 未来已经到来——只是尚未均匀分布。

当我思考 AI 能做什么、不能做什么时，我就会想起这句话。今天，AI 的进展极不均衡。有些事——生成代码、文本、图像——实现了量子式跃升，它们以 AI 速度运行。另一些事——与客户交谈、发现他们的需求、说服他们购买——仍以人类速度推进。

这种不均衡的分布正在重塑产品团队。聚光灯正从实现类工作转向理解类工作。那些一直让最优秀的 PM 脱颖而出的核心技能——理解用户需求、清晰地定义问题、设计优雅的解决方案——已经变得成倍地更有价值。

最优秀的 PM 会把这些洞察转化为规格说明——这样的规格说明能对齐团队、指导实现，并在一个日益自动化的开发世界中成为持久的产物。

## 要点回顾

- 规格说明（spec）正从「走过场的文书」变成产品管理的基石，乃至新的源代码。
- 吴恩达观察到公司开始需要更多而非更少的 PM，印证了「工程师变快后，瓶颈转移到该构建什么」。
- Sean Grove 的论点：代码是对规格说明的「有损投影」，只有规格说明能同时对齐人与机器。
- 原型工具（v0、Lovable、Replit）没有杀死规格说明，反而让规格说明成为产出：先原型、再反馈、再写清晰的规格说明。
- 规格驱动开发的实例：非技术创始人用 Linear + VS Code + GitHub Copilot + Claude Sonnet 4 + Linear MCP，在几分钟内上线一个页头按钮。
- 三个必要条件：具体明确、有所选择、有工程师把关。
- AI 的进展并不均衡：生成类工作以 AI 速度前进，理解与决策类工作仍以人类速度推进，PM 的核心技能因此更值钱。
